# 效能與記憶體評估

本文記錄 collector 的效能瓶頸量測、記憶體使用評估，以及「是否需要改用 Rust」
的結論。所有數字都是實際量到的，不是估算。

## 量測環境

| 項目 | 值 |
|---|---|
| CPU | Intel Xeon @ 2.10GHz, 4 vCPU |
| Python | 3.11.15 |
| pysnmp | 6.2.6 (pyasn1 0.6.0) |
| 被測設備 | snmpsim 模擬器，走 loopback |
| 小型設備 | 3 介面、2 個 LLDP 鄰居 |
| 大型設備 | 1000 介面、500 個 LLDP 鄰居 |

因為走 loopback，網路延遲接近 0。真實環境的 wall time 會比這裡高（要等 UDP
往返），但 **CPU 時間是下限，不會因為網路變快而減少**，所以 CPU 數字可以直接
拿來推估容量。

---

## 1. 瓶頸在哪裡：每個請求都重建一個 SNMP engine

改動前，`_snmp_get()` 和 `_snmp_walk()` 各自 `SnmpEngine()` 建一個新 engine、
用完就 `closeDispatcher()`。一次完整的 `poll_device()` 會發 17～26 個請求，
所以一台設備一輪就建了 20 幾個 engine。

單獨量測 `SnmpEngine()` 的成本：

```
1st engine :    26.0 ms
2nd engine :    24.5 ms   <- MIB 不會跨 engine 快取
100 engines:  +63.55 MiB  -> 約 650 KiB/engine
```

cProfile 顯示 **74% 的時間花在 `builtins.compile`**：pysnmp 每建一個 engine
都重新讀取並重新編譯內建的 MIB 模組原始碼（13 個模組、279 個符號）。這是純
CPU 工作，而且是在 event loop 的執行緒上同步跑的，所以它會**擋住**所有其他
設備的輪詢。

### 改動：每個 collector 共用一個 engine

`SNMPCollector` 改為延遲建立一個 engine 並重複使用，加上 `aclose()` 和
async context manager。`app/collector.py` 改成每台設備一個
`async with SNMPCollector(...)`，所以「一台設備 = 一個 engine = 一個 UDP
socket」，輪詢完立刻釋放。

同時把 LLDP port 對應、CDP、介面統計都要用的 `ifDescr` / `ifName` 在單次
`poll_device()` 內快取起來（只快取這兩張表，見下面的記憶體評估）。

### 實測結果（同一台小型設備，完整 poll_device）

| | 改動前 | 改動後 | 倍數 |
|---|---|---|---|
| 建立的 engine 數 | 23 | **1** | 23× |
| wall time | 1938 ms | **221 ms** | 8.8× |
| user CPU | 1758 ms | **116 ms** | **15×** |
| RSS 增量 | +5.23 MiB | +1.95 MiB | 2.7× |

解析出來的鄰居、介面、管理 IP **完全相同**，沒有行為變化。

注意改動前 1938 ms 裡有 1758 ms 是 CPU——在一個零延遲的 loopback 上。這代表
原本的瓶頸從頭到尾都不是網路，而是重建 engine。`COLLECTOR_CONCURRENT=20` 在
這種情況下幾乎沒有用，因為 20 個協程全部排隊等同一個執行緒做 MIB 編譯。

## 2. 記憶體評估

### 2.1 每一列走訪結果的成本

```
  100 rows: 614 B/row
 1000 rows: 500 B/row
 5000 rows: 378 B/row   (OctetString)  /  558 B/row (Counter64)
```

一列 = 索引字串 + pysnmp 的值物件，約 **400～600 bytes**。

這代表 `get_interface_stats()` 對一台 1000 介面的設備走訪 4 個欄位時，同時
握有約 4000 列 ≈ **2 MiB**；5000 介面的機框會到 10 MiB。這比 engine 本身
(650 KiB) 大得多，**走訪結果才是記憶體的主要持有者**。

因此 `ifDescr` / `ifName` 的快取刻意加了兩道限制：

- 只快取 `_CACHEABLE_WALK_OIDS` 這兩張表，不是所有走訪結果
- 超過 `_WALK_CACHE_MAX_ROWS = 2000` 列就用完即丟，不留在快取裡

快取只在 `poll_device()` 執行期間存在，結束就清掉，不會跨輪保留。快取鍵包含
IP，所以不可能把一台設備的介面表餵給另一台。

### 2.2 併發輪詢的尖峰記憶體

| 情境 | wall | CPU | 尖峰 RSS | 相對 idle |
|---|---|---|---|---|
| idle（載入完成） | – | – | 50.9 MiB | – |
| 1× 小型 | 0.25s | 0.13s | 53.0 MiB | +2.1 MiB |
| 20× 小型併發 | 3.49s | 2.69s | 95.7 MiB | +42.6 MiB |
| 1× 大型（1000 介面） | 3.63s | 1.43s | 93.7 MiB | +0.0 MiB |
| 5× 大型併發 | 10.58s | 7.58s | 93.2 MiB | +0.5 MiB |
| 20× 大型併發 | 44.70s | 34.46s | **176.4 MiB** | +84.5 MiB |

最壞情況（20 台 1000 介面設備同時輪詢）尖峰 176 MiB。換算下來每一個併發的
大型設備約 **4.2 MiB**。

### 2.3 有沒有洩漏？

連續 10 輪、每輪 10 台大型設備：

```
cycle  1: 150.2 MiB      cycle  6: 171.5 MiB
cycle  2: 168.2 MiB      cycle  7: 142.6 MiB
cycle  3: 184.3 MiB      cycle  8: 143.5 MiB
cycle  4: 142.6 MiB      cycle  9: 141.6 MiB
cycle  5: 171.5 MiB      cycle 10: 173.5 MiB

第 5 輪 -> 第 10 輪：+1.95 MiB
```

RSS 在 141～184 MiB 之間震盪、**沒有趨勢**（第 7～9 輪比第 1 輪還低）。
tracemalloc 顯示 Python heap 的淨成長只有約 0.8 MiB，而且全部落在 `ply/yacc.py`
（pysmi 的 MIB parser 表，一次性建立）。**沒有記憶體洩漏。**

震盪的原因是 glibc 不會立刻把釋放的 arena 還給 OS——單獨量測
`closeDispatcher()` 時，63 MiB 只有 14 MiB 馬上回到 OS。所以 RSS 看起來高於
實際活躍資料量，這是正常的高水位現象，不是漏。

### 2.4 結論：記憶體不是問題

- collector 容器 **512 MiB 很充裕**，256 MiB 對一般園區網路也夠
- 真要壓低，調 `COLLECTOR_CONCURRENT` 就是線性有效的旋鈕（每個併發大型設備
  約 4.2 MiB）
- 不需要為了記憶體換語言

## 3. 真正的上限是 CPU

> **注意：這一節的容量推估已被第 7 節取代。**
> 下面的「~170 台」是用「每台都是 1000 埠機框」外推的，那種機隊在實體上
> 不存在。以真實接線架構重算的結果見第 7 節（單一行程 ~3000 台接取交換機），
> 以及第 8 節 —— 先撞牆的其實是資料庫，不是 CPU。


改動後，20 台大型設備併發花 34.46s **CPU**（wall 44.70s，CPU 佔 77%）。
也就是一台 1000 介面的設備每輪要燒掉約 **1.7 秒的 CPU** 來做 ASN.1 解析和
物件配置。這部分無法用 asyncio 疊起來——它是單執行緒的實際運算。

用 `COLLECTOR_INTERVAL=300` 推估**單一 Python 行程**的容量：

| 設備類型 | 每輪 CPU/台 | 300 秒內大約可容納 |
|---|---|---|
| 小型接取交換機（約 48 埠） | 0.13 s | ~2300 台 |
| 大型機框（1000 埠、500 鄰居） | 1.7 s | **~170 台** |

（留 10～20% 餘裕給 topology/alert engine 和 DB 寫入。）

這就是判斷要不要上 Rust 的分界線。（修正後的分界線見第 10 節。）

## 4. Python + Rust 拆分評估

### 結論：現在不需要，而且不要整個重寫

> 這一節的結論在第 10 節重新驗證過，結論不變但理由換了：原本寫的
> 「反正是 I/O-bound」是錯的（實測是 CPU 佔 77%），真正的理由是
> SNMP 那一段可以靠行程分片線性擴展。


理由：

1. **這次真正的 bug 是依賴版本漂移，不是語言問題。** 收不到 LLDP 的原因是
   pysnmp 4.x → 6.x 的 API 破壞性變更（`nextCmd` 的回傳從 varBind 變成
   varBindTable），加上沒有鎖版本、也沒有靜態型別檢查去攔。Rust 的型別系統
   確實會在編譯期抓到這個錯——但 `pyright` + lockfile 也會，而且成本低兩個
   數量級。
2. **效能問題已經解決了 15 倍，而且是改架構不是換語言。** 原本的瓶頸是重建
   engine，不是 Python 慢。
3. **記憶體完全沒問題**（見第 2 節）。
4. **這個專案的價值在各廠牌 MIB 的怪癖處理**（LLDP subtype、`lldpRemLocalPortNum`
   對應、`lldpRemManAddrTable` 索引裡的管理 IP、各家 CPU OID），那是知識而不是
   程式碼，重寫最容易漏掉。Rust 的 SNMP crate 生態明顯比 pysnmp 薄，SNMPv3 的
   auth/priv 套件支援尤其要先確認——從「難搞但完整」換到「乾淨但可能缺功能」
   是真實的風險。
5. **API 層（FastAPI + SQLAlchemy）完全沒有效能問題**，沒有任何理由動它。

### 比 Rust 更划算的下一步（依序）

1. **鎖死依賴**：用 `pip-compile` 產生含 hash 的 lock 檔。這次事故的根因。
2. **靜態型別檢查**：`pyright` 進 CI。
3. **行程分片**：collector 已經是獨立容器，起 N 個各負責 1/N 的設備就繞過 GIL
   了，架構上已經支援，不需要改程式。這是最便宜的水平擴充。
4. **錯開輪詢**：目前是每 300 秒一次把所有設備打出去。改成在週期內均勻分散，
   尖峰記憶體和 CPU 都會下降。
5. **只抓需要的介面**：目前 `get_interface_stats()` 走訪整張 ifTable 的 4 個
   欄位。只抓有 LLDP 鄰居的介面，對大型機框的省幅很大。

### 什麼時候才真的該上 Rust

當以上都做完，而且**量到**單一行程撐不住時——參考第 3 節，大約是
**超過 170 台 1000 埠等級的設備、又要求 5 分鐘輪詢**的規模。

那時候正確的做法是**只把 collector 換成 Rust 單一執行檔**，讀寫同一個
Postgres，API 和前端留在 Python：

- collector 是唯一對效能敏感的部分
- collector 是唯一可以獨立替換的部分（它和 API 之間只透過 DB 溝通）
- 可以漸進遷移：先讓 Rust collector 接管一部分設備，兩者並存

**不要**把 API、topology engine、alert engine 一起重寫——它們不是瓶頸。

## 5. 設備不回應時的退避

無回應的設備是輪詢週期裡最貴的東西：每一個 OID 都要等滿
`SNMP_TIMEOUT × (SNMP_RETRIES + 1)`。以預設值（5 秒 × 3）計算，光
`get_device_info()` 的 3 個 GET 就是 **45 秒**，而且每輪都付一次、永遠拿不到
資料。

`app/core/poll_scheduler.py` 的 `OfflineBackoff` 會依連續失敗次數拉長間隔：

| 連續失敗次數 | 下次嘗試間隔（預設） |
|---|---|
| 1 | 300s（等於正常週期，不延遲） |
| 2 | 600s |
| 3 | 1200s |
| 4 以上 | 1800s（上限） |

第一次失敗**不會**造成任何延遲，所以偶發的一次 timeout 沒有代價；只有持續
失敗的設備才會被退避。時間來源是 `time.monotonic()`，不受 NTP 跳時或日光
節約時間影響。

### 設定

| 環境變數 | 預設 | 說明 |
|---|---|---|
| `COLLECTOR_OFFLINE_BACKOFF` | `true` | 設 `false` 可關閉，恢復每輪都探測 |
| `COLLECTOR_OFFLINE_BACKOFF_MAX` | `1800` | 退避間隔上限（秒） |

被跳過的設備狀態維持 `offline`，不會因為沒探測就變成 unknown。每輪的 INFO
log 會顯示跳過幾台，DEBUG log 會顯示每一台還要等多久。

### 狀態存在記憶體裡（刻意的）

這個專案用 `Base.metadata.create_all` 建表、**沒有 migration 機制**
（沒有 alembic 目錄）。在 `devices` 加欄位會讓所有既有部署在下一次 SELECT
就壞掉。所以退避狀態只存在 collector 行程的記憶體裡。

代價：collector 重啟後，每台離線設備會多被探測一輪。可以接受。

記憶體方面，每輪會呼叫 `prune()` 清掉已刪除設備的狀態，所以長時間執行不會
累積。每台失敗設備的狀態是一個只有兩個欄位的 dataclass。

# 以 500+ 台為基準點的重新評估

前面第 3、4 節的容量推估是用「單台設備外推」做的，那個做法會高估，因為它
假設每台設備都是 1000 埠 / 500 鄰居的機框。實際的實體接線架構不可能長這樣
（500 台這種設備等於 25 萬條線）。這一節改用**整個機隊**的量測重算一次，
並且把資料庫那一段也納進來 —— 結論和前面不一樣。

## 6. 唯一真正重要的常數：每列 138 µs

把 collector 用到的 15 張表逐一計時（大型機框，1000 介面 / 500 鄰居）：

| 走訪 | 列數 | CPU ms | µs/列 |
|---|---|---|---|
| lldpRemChassisId | 500 | 65.9 | 132 |
| lldpRemChassisIdSubtype | 500 | 78.8 | 158 |
| lldpRemPortId | 500 | 79.7 | 159 |
| lldpRemPortIdSubtype | 500 | 76.3 | 153 |
| lldpRemPortDesc | 500 | 66.7 | 133 |
| lldpRemSysName | 500 | 67.8 | 136 |
| lldpRemManAddr | 500 | 69.2 | 138 |
| lldpLocPortDesc | 500 | 66.2 | 132 |
| lldpLocPortId | 500 | 67.3 | 135 |
| lldpLocPortIdSubtype | 500 | 64.2 | 128 |
| ifName | 1000 | 124.7 | 125 |
| ifDescr | 1000 | 137.1 | 137 |
| ifHighSpeed | 1000 | 159.3 | 159 |
| ifHCInOctets | 1000 | 124.5 | 124 |
| ifHCOutOctets | 1000 | 137.1 | 137 |
| **合計** | **10000** | **1384.8** | **138** |

成本和表的種類無關，平得像一條線。這就是 pysnmp 解碼一列的硬成本。於是：

```
每台每輪 CPU ≈ 30 ms（固定）+ 138 µs × 走訪列數
走訪列數      = 10 × 鄰居數 + 5 × 介面數
```

驗證（兩種設備，誤差 < 3%）：

| 設備 | 介面 | 鄰居 | 預測列數 | 預測 CPU | 實測 CPU |
|---|---|---|---|---|---|
| 大型機框 | 1000 | 500 | 10000 | 1410 ms | 1381 ms |
| 接取交換機 | 48 | 4 | 280 | 69 ms | 70 ms |

**關鍵在於這個公式沒有一項跟設備數有關，只跟「實體線數」和「埠數」有關。**
`10 × 鄰居數` 是你機房裡實際插了幾條線決定的，不是 CPU 速度決定的。

## 7. 500 台實際要燒多少

機隊組成取一個真實的校園／園區網路：1 台核心 + 8 台匯聚（96 埠 / 62 鄰居）
+ 491 台接取（48 埠 / 20 鄰居，含 IP 電話與 AP）。

| 項目 | 每輪 |
|---|---|
| 走訪列數（全機隊） | ~225,000 |
| SNMP 解碼 CPU | 31.1 s |
| 每台固定成本 × 500 | 15.0 s |
| **SNMP 合計** | **46 s** |

300 秒週期裡佔 **15% 的一顆核心**。Python 在 500 台這個量級完全不吃緊。

前面第 3 節說「單一行程 ~170 台」是錯的推估基準 —— 那是 500 台全都是
1000 埠機框的假設。以實際接線架構來算，單一 Python 行程在 300 秒週期內
可以處理 **~3000 台**接取交換機。

## 8. 真正先撞牆的是資料庫，不是 Python

> **這一節描述的是改動前的狀態。索引、每台一個 session 與發現快取已經
> 做掉了（第 13 節），改前/改後的實測數字在第 14 節。**

`poll_single_device()` 對**每個鄰居每一輪**都發一次查詢：

```python
select(RawLink).where(RawLink.local_device_id == device.id,
                      RawLink.local_port == neighbor.local_port,
                      RawLink.remote_hostname == neighbor.remote_hostname)
```

而 `raw_links` **除了主鍵之外沒有任何索引**（`app/models/link.py`），
`merged_links` 的 `(device_a_id, device_b_id)` 也沒有 —— 而
`update_merged_links_in_db()` 每輪對每條 merged link 查一次。
所以每次查詢都是全表掃描，而查詢次數又和表的列數同步成長：**平方級**。

另外 `auto_discover_neighbor()` 預設開啟（`auto_discover` 預設 `True`），
每個鄰居每輪再加兩次 `devices` 查詢。

真實 PostgreSQL 16 實測一輪的資料庫時間（20 鄰居/台）：

| 設備數 | raw_links 列數 | 查詢次數 | 無索引 | 加索引 | 改善 |
|---|---|---|---|---|---|
| 50 | 1,042 | 2,084 | 1.30 s | 1.12 s | 1.2× |
| 100 | 2,042 | 4,084 | 2.63 s | 2.26 s | 1.2× |
| 250 | 5,168 | 10,336 | 9.79 s | 5.53 s | 1.8× |
| 500 | 10,336 | 20,672 | **23.04 s** | 13.23 s | 1.7× |
| 1000 | 20,672 | 41,344 | **56.58 s** | 26.68 s | 2.1× |

設備數 20 倍（50→1000），無索引的時間變成 **43.5 倍** —— 平方項確認存在。
加了索引之後成長回到接近線性（23.8 倍 / 20 倍）。

### 8.1 併發對資料庫那一段完全無效

`poll_all_devices()` 把**同一個 `db` session** 傳給所有併發的 device poll。
SQLAlchemy 的 `AsyncSession` 不支援併發操作，它會在內部序列化（實測不會報錯，
但也完全不會平行）。500 台、已加索引：

| COLLECTOR_CONCURRENT | 共用 session（現狀） | 每台一個 session |
|---|---|---|
| 1 | 10.60 s | 11.43 s |
| 10 | 12.23 s | 7.40 s |
| 20 | 11.74 s | 7.52 s |
| 40 | 12.64 s | 8.24 s |

**把併發從 1 開到 40，資料庫那一段一秒都沒有變快。** 這是設計上的硬序列化點。
改成每台一個 session 之後併發才開始有作用（1.6×）。

### 8.2 500 台的完整帳

| 項目 | 每輪（現狀） | 每輪（修掉索引+session） |
|---|---|---|
| SNMP 解碼 | 46 s | 46 s |
| 資料庫 | 23 s | 7.5 s |
| 合計 / 300 s 週期 | **69 s（23%）** | **54 s（18%）** |

## 9. 有一段 CPU 是純浪費

> **已修正（第 13.3 節）。** 那 9.8 s/輪不再是浪費：`ifHighSpeed` 現在
> 真的接到每條線路的頻寬上，`ifHCIn/OutOctets` 算成真實的 bps 與使用率。
> 只要接線盤點、不要流量的部署可以用 `COLLECTOR_TRAFFIC_STATS=false`
> 關掉那兩張表的走訪，而仍然保留真實埠速。

`get_interface_stats()` 每輪在每台設備上走訪 `ifDescr`、`ifHighSpeed`、
`ifHCInOctets`、`ifHCOutOctets`，**而它的回傳值沒有任何人使用** ——
`app/collector.py:291` 只拿它的 `len()` 印一行 log。全專案沒有其他地方讀它
（沒有 InterfaceStats 資料表，API 也沒有這個端點）。

而 `topology_engine.py` 計算連結頻寬的方式是**從埠名字串猜**：

```python
bandwidth = self._estimate_bandwidth(link.local_port)
port_details.append(PortInfo(..., in_bps=0,   # Will be updated by collector
                                  out_bps=0))
```

那行註解裡的 "will be updated by collector" 從來沒有發生。所以現在的狀況是：
**真正的 `ifHighSpeed` 被抓回來丟掉，然後用埠名去猜一個值；流量使用率永遠是 0。**

成本：500 台機隊每輪 `3 × 48 × 491 ≈ 71,000` 列 = **9.8 s CPU**，
佔 SNMP 總時間的 21%，換到的資料是沒人看的。

這一點直接牴觸這個專案「最簡單最快速**最準確**」的初衷 —— 而且它不是語言問題，
Rust 重寫一遍只會讓同一筆沒人要的資料算得更快。

## 10. 修正後的 Rust 結論

以 500 台為基準點，把兩邊放在一起看：

| | Rust 能改善的 | Rust 改善不了的 |
|---|---|---|
| 500 台 | 31 s 解碼 → ~2 s | 23 s 資料庫、15 s 固定成本 |
| 1000 台 | 62 s 解碼 → ~3 s | 57 s 資料庫（且是平方成長） |

**在 500 台，用 Rust 重寫 collector 能拿回 300 秒預算裡的 10%；
補兩個索引加改 session 生命週期能拿回 5%；刪掉沒人用的那段走訪能拿回 3%。**
後兩項合起來跟 Rust 同一個量級，但一個是幾十行，一個是連 SNMPv3 都要重做的重寫。

更重要的是成長的形狀：SNMP 那一段是**線性**的，而且 collector 已經是獨立容器，
**起 N 個行程各管 1/N 台設備就直接線性擴展，不用改一行程式** —— 這正是 Rust
會給你的東西。資料庫那一段是**平方**的，而且分片分不掉（共用同一個 Postgres），
所以它才是那個會先撞牆的。

結論沒變但理由換了：**不是因為「反正是 I/O-bound」（那個說法我前面講錯了），
而是因為 Python 這一段可以靠分片線性擴展，而先撞牆的那一段換成 Rust 也一樣會撞。**

真的該考慮 Rust 的時機：已經分片到多台主機、資料庫那層也修完了、而你想減少
主機數量 —— 大約在 2000 台以上。即使那時候，也只換 collector 執行檔
（它只透過 Postgres 跟其他元件講話，可以和 Python 版並存漸進遷移），
API、topology engine、alert engine 留在 Python。

### 索引有一個部署上的陷阱

本專案沒有 migration 機制，只用 `Base.metadata.create_all()`。實測確認：

```
既有資料表 + 模型新增索引 → create_all() 不會建立該索引
全新資料庫              → 會建立
```

`create_all(checkfirst=True)` 看到表已存在就整張跳過，不會比對索引。所以第 1 項
**不能只改模型**，否則你現有的部署升級後會繼續用全表掃描而且毫無徵兆。必須在
啟動時發明確的 `CREATE INDEX IF NOT EXISTS` DDL。

> 這一點已經做掉了，而且範圍比索引更大 —— 新增的欄位也有同樣的問題。
> 做法與升級路徑實測見第 13.1 節。

## 13. 這次改了什麼

### 13.1 兩個索引，以及既有資料庫怎麼真的拿到它

模型上加了：

```python
# raw_links —— poll_single_device() 每個鄰居每輪就查這三欄一次
Index("ix_raw_links_lookup", "local_device_id", "local_port", "remote_hostname")
# merged_links
Index("ix_merged_links_pair", "device_a_id", "device_b_id")
```

但第 11 節講的陷阱是真的：`create_all(checkfirst=True)` 看到表已存在就整張跳過。
所以 `init_db()` 之後多跑一段 `_sync_upgrade_schema()`，用 SQLAlchemy inspector
比對「模型上有、資料庫裡沒有」的欄位與索引，然後只做兩種能安全就地套用的動作：

- 新的**可為 NULL 欄位** → `ALTER TABLE ... ADD COLUMN`
- 新的**索引** → `CREATE INDEX IF NOT EXISTS`（PostgreSQL ≥ 9.5、SQLite ≥ 3.8 都支援）

其他的（刪欄位、改型別、對已有資料的表加 NOT NULL 欄位）只記一行 warning 就不動，
那種需要真正的 migration。

用「前一版建立的資料庫 + 一列真實資料」實測升級路徑：

```
== raw_links ==
  新增欄位： ['bandwidth_mbps', 'in_bps', 'in_octets', 'out_bps', 'out_octets', 'sampled_at']
  索引 before: ['ix_raw_links_id']
  索引 after : ['ix_raw_links_id', 'ix_raw_links_lookup']
== merged_links ==
  索引 before: ['ix_merged_links_id']
  索引 after : ['ix_merged_links_id', 'ix_merged_links_pair']

既有資料列保留： 1
升級後的查詢計畫： SEARCH raw_links USING INDEX ix_raw_links_lookup
                   (local_device_id=? AND local_port=? AND remote_hostname=?)
```

最後一行是重點：升級前這句是全表掃描，升級後走索引。**升級不需要人工介入，
也不會動到既有資料。** collector 容器自己也會跑這段（`_prepare_database()`，
失敗重試三次），因為它可能比 app 容器先起來，而索引正是讓它不退化成全表掃描的東西。

### 13.2 每台設備一個 DB session

改前：`poll_all_devices()` 把**同一個 `db`** 傳給所有併發的 `poll_single_device()`。
`AsyncSession` 不支援併發，但它不報錯 —— 它內部序列化。所以 `COLLECTOR_CONCURRENT`
對資料庫那半邊完全沒有作用（第 8.1 節）。

改後：每台設備在自己的 session 裡取得、更新、commit。相關的連帶修正：

- 連線池大小改成 `max(10, COLLECTOR_CONCURRENT + 5)`。否則併發上限只是變成
  在連線池上排隊。
- 自動發現的 insert 走**另一個**短命 session，並且用一個大小 4 的 semaphore
  限流。新鄰居的 insert 不應該因為撞到 hostname 唯一鍵就讓那台設備整輪的
  連線資料一起 rollback；而第一輪全機隊都是新設備時，也不該要求兩倍連線數。
- 那個 insert 的 `IntegrityError` 單獨接住：多行程分片時兩個行程會同時發現
  同一台新設備，先到的贏，後到的把它記進快取就好。

### 13.3 真實頻寬與真實流量

資料存在 `raw_links` 上，而不是新開一張表 —— 因為 `raw_links` 的每一列就是
**一條實體線路的一端**，而它每輪本來就會被讀一次寫一次，所以多存這幾欄不增加
任何查詢：

```python
bandwidth_mbps    # ifHighSpeed，設備自己報的埠速
in_octets/out_octets   # 上一次的計數器讀值
in_bps/out_bps         # 由兩次取樣算出來的速率
sampled_at             # 上一次取樣的時間
```

`ifHCInOctets` 是**累計計數器不是速率**，速率只存在於兩次取樣之間。
`app/core/traffic.py` 的 `counter_rate()` 負責這件事，而且在算不出來的時候
回傳 `None` 而不是 `0` —— 「還沒量到」和「沒有流量」是兩件不同的事：

| 情況 | 回傳 |
|---|---|
| 正常：300 s 內 +37.5 MB | `1,000,000` bps |
| 這個埠的第一次取樣 | `None` |
| 計數器倒退（設備重開/清計數器） | `None` |
| 閒置埠，兩次讀值相同 | `0` |
| 兩次取樣間隔 > 4 小時 | `None` |
| 兩次取樣間隔 < 1 秒 | `None` |
| 上一筆時間戳帶時區（PostgreSQL）、這一筆不帶（naive） | 正常計算 |
| 10G 埠跑滿線速 | `10,000,000,000` bps |

計數器倒退一律當成重置，不當成繞回：64 位元 octet 計數器在 100 Gbps 下要
約 46 年才繞一圈。時區那一列是必要的 —— 同一個欄位從 SQLite 讀回來是 naive，
從 PostgreSQL 的 `timestamptz` 讀回來帶時區，兩者相減會直接 `TypeError`。

鄰居對應到介面：**先用 ifIndex**（LLDP 收集階段已經解析出來，不會有歧義），
名稱只是備援（有些設備的 `lldpLocPortTable` 對不回 ifIndex）。`ifName` 和
`ifDescr` 兩種拼法都收（`Gi1/0/1` 與 `GigabitEthernet1/0/1`），而這兩張表
本來就在 per-poll 快取裡，所以這一步沒有多走訪任何東西。

成本面：`ifDescr`/`ifName` 來自快取，所以這一段真正的成本只有 `ifHighSpeed`
加上（開啟流量時）兩張 octet 表。`COLLECTOR_TRAFFIC_STATS=false` 會關掉那兩張，
**但仍然保留真實的 `ifHighSpeed`** —— 只要接線盤點、不要流量的部署，準確度不打折。

### 13.4 auto-discover 快取

改前每個鄰居每輪固定兩次 `devices` 查詢（hostname、ip_address），500 台約
兩萬次，而答案在輪與輪之間幾乎不變。改後在每輪開始時用**一次**
`SELECT hostname, ip_address FROM devices` 把整個機隊載進記憶體（含 excluded
的設備，否則被排除的設備會立刻被重新發現再加回來）。

`DiscoveryCache` 同時記住「轉不成設備的鄰居」（沒有管理位址、DNS 查不到、
SNMP 不回應 —— IP 話機、印表機、關掉 SNMP 的 AP），預設一小時內不再探測，
過期後會再試，所以後來才變得可達的設備不會被永久忽略。它的 `claim()` 也兼作
鎖：兩台設備在同一輪看到同一個新鄰居時，只有一個會去解析、探測、insert。

兩輪的實測（`sw1`/`sw2` 加上一個 AP 與一個對不到的 `Po1` 鄰居）：

```
第 1 輪 DNS 查詢： ['ap-lobby', 'sw9']
第 2 輪 DNS 查詢： []            <- 快取回答，沒有碰網路
```

### 13.5 順手修掉的兩個準確度問題

**一、頻寬被算成兩倍。** 兩端都納管時，同一條線會被兩邊各報一次，而
`merge_links()` 把群組裡所有 raw link 的頻寬相加 —— 於是兩條 1G 線被算成
4000 Mbps，而所有由它推導出來的使用率都只有真值的一半。改成只採信一端
（看到比較多條線的那一端；用埠名去配對兩端的報告不可靠，一端叫 `Gi1/0/1`
另一端叫 `GigabitEthernet1/0/1`）。兩輪端對端實測：

```
兩條 1G 線、兩端都有回報 -> total_bandwidth_mbps=2000（不是 4000）
in=1,995,650 bps（預期 2,000,000）  out=3,991,302（預期 4,000,000）
util_in=0.0998%  util_out=0.1996%
```

差的 0.2% 不是誤差而是正確行為：速率是用**兩次取樣的實際間隔**除的，
這個測試的兩輪相距 300.5 秒而不是 300.0 秒。

**二、「0%」不等於「沒量到」。** 使用率現在可以是 `null`，API 照實傳，
前端顯示 `—` 而不是 `0%`。重開 collector 後的第一輪必然沒有速率
（速率需要兩次取樣），那時候畫 0% 就是在報一個它不知道的數字。
`port_details` 另外多了 `speed_source`（`ifHighSpeed` 或 `port_name`），
所以看得出哪些埠的速度是真讀的、哪些是猜的。

順帶的效果：`alert_engine.check_link_utilization()` 本來就存在，但因為使用率
永遠是 0，**線路使用率告警從來沒有可能觸發過**。現在它有真實輸入了。

HTTP 層實測（`GET /api/v1/topology/?view=full`）：

```json
{
  "total_bandwidth_mbps": 2000,
  "utilization_in_percent": 0.0997825,
  "port_details": [
    {"local_port": "Gi1/0/1", "remote_port": "GigabitEthernet1/0/24",
     "bandwidth_mbps": 1000, "in_bps": 997825, "out_bps": 1995651,

  ]
```

## 14. 500 台實測：改前 vs 改後

機隊：1 核心（96 埠 / 8 鄰居）+ 8 匯聚（96 埠 / 62 鄰居）+ 491 接取
（48 埠 / 20 鄰居，1 條上行 + 19 個端點設備）= 10,324 條 raw link。
PostgreSQL 16.13，SNMP 層換成不送封包的替身，所以表格裡的時間就是
**一輪裡資料庫那半邊的 wall time**。取第 2、3 輪的平均（穩定狀態）。

### 14.1 併發掃描

| `COLLECTOR_CONCURRENT` | 改前 | 改後 | 倍數 |
|---|---|---|---|
| 1 | 37.13 s | **18.61 s** | 2.00× |
| 20 | 29.02 s | **13.18 s** | 2.20× |
| 40 | 29.89 s | **13.60 s** | 2.20× |

每輪發出的 SQL 敘述數：改前 27,561（併發 1 時 37,509），改後 **24,000**。

兩件事要分開看：

- **索引 + 發現快取**本身就給了 2.0×（併發 1：37.13 → 18.61 s）。這是完全
  不依賴併發的那一半。
- **每台一個 session** 讓併發開始有作用。改前從併發 1 開到 20 只快 1.28 倍
  （37.13 → 29.02），改後是 1.41 倍（18.61 → 13.18）。幅度不大，但方向對了。

**併發開到 40 在兩個版本都沒有再變快。** 剩下的序列化點是合併與告警那一段
（它們跑在單一 session 裡），所以 `COLLECTOR_CONCURRENT` 調超過 20 對資料庫
那半邊沒有幫助 —— 這點改完之後依然成立，不要以為調大就會更快。

### 14.2 500 台的新帳

| 項目 | 改前 | 改後 |
|---|---|---|
| SNMP 解碼（第 7 節） | 46 s | 46 s |
| 其中沒人使用的走訪（第 9 節） | 9.8 s | 0 s（資料接上了，不再是浪費） |
| 資料庫 | 29 s | 13 s |
| 每輪合計 | 75 s | **59 s** |
| 佔 300 秒週期 | 25% | **20%** |

SNMP 那一段沒有變快 —— 本來就沒打算讓它變快，第 10 節已經說明理由
（它是線性的，而且靠行程分片就能擴展）。真正的變化是：**那 9.8 s 現在換到了
真實的埠速與真實的流量**，而原本會隨機隊平方成長的那一段不再那樣成長。

### 14.3 平方成長有沒有真的消失

這是第 8 節最重要的那個問題。同一支驅動、同一個機隊模型，只換設備數：

| 設備數 | raw links | 改前 | 改後 | 改後倍數 |
|---|---|---|---|---|
| 250 | 5,324 | 14.85 s | **7.41 s** | 2.00× |
| 500 | 10,324 | 31.26 s | **13.78 s** | 2.27× |
| 1000 | 20,324 | 73.26 s | **26.12 s** | 2.80× |

把它換算成「每條線路的成本」才看得清楚 —— 這才是判斷成長形狀的方式：

| 設備數 | 改前 每條線 | 改後 每條線 |
|---|---|---|
| 250 | 2.79 ms | 1.39 ms |
| 500 | 3.03 ms | 1.34 ms |
| 1000 | 3.60 ms | **1.29 ms** |

**改前每條線的成本隨機隊變大而上升 29%（2.79 → 3.60 ms），改後是平的、
甚至微降 8%（1.39 → 1.29 ms）。** 以線路數為底的成長指數從 1.19 降到 0.94。

平的那條線就是答案：**原本那個「表越大、每次掃描越貴、而掃描次數又隨表變多」
的平方項消失了。** 也因為這樣，改前改後的差距隨規模放大 —— 250 台只快 2.0 倍，
1000 台快 2.8 倍。

（註一：改前的指數 1.19 比第 8 節純查詢重放量到的更接近線性，因為這裡量的是
一整輪，裡面有大量成本是線性的寫入，把平方項稀釋了。平方項本身沒有變，
只是在完整的一輪裡佔比沒那麼極端。）

（註二：500 台這一列的數字和 14.1 的表略有差異（13.78 對 13.18 s），因為
是不同批次跑的。同一組設定重跑的變異大約 4% —— 量測機器是共用的，
所以表格之間差幾個百分點不要當成訊號。）

## 15. 要不要在資料庫前面掛 Redis

先講一個事實：**Redis 已經在這個專案裡了，而且完全沒有被用到。**
`docker-compose.yml` 起了一個 `redis:7-alpine`、`requirements.txt` 有
`redis>=5.0.0`、`config.py` 有 `redis_url` —— 然後 `grep -rn redis app/`
只有 config 那一行。所以這題其實是「要不要開始用它」，基礎設施成本是零，
只有程式複雜度的成本。

要回答，得先問**它到底要快取什麼**。以下都是實測（Redis 7.0.15 走 loopback、
PostgreSQL 16.13、20,324 列的 `raw_links`，每種做法 2000 次；最右欄換算成
500 台機隊一輪的 10,324 條線）。

### 15.1 collector 的讀取路徑：不要

collector 每輪對每個鄰居做的那次 `raw_links` 查詢，查的是**它自己上一輪寫的
資料**。它是唯一的寫入者。

| 做法 | 每次 | 一輪（10,324 次） |
|---|---|---|
| PostgreSQL SELECT（已加索引，一次一句，經 ORM） | 579.1 µs | 5.98 s |
| Redis GET，一次一個 round trip | 104.1 µs | 1.07 s |
| Redis MGET，每 200 個一次 round trip | 5.0 µs | 0.05 s |
| **行程內 dict** | **< 0.1 µs** | **~0 s** |

Redis 的確比現在的 ORM 查詢快 5.6 倍。但**行程內的 dict 比 Redis 又快三個
數量級**，因為它連 syscall 都不用。而既然 collector 是那份資料的唯一寫入者，
它本來就可以把整份對照表留在記憶體裡（500 台約 10,324 條、每條幾百位元組，
就是幾 MB —— 第 2 節量過記憶體不是這個系統的限制）。

**所以如果要快取這一段，答案是行程內快取，不是 Redis。** 掛 Redis 只是把一個
不需要網路的查詢變成一個需要網路的查詢。順帶一提，這 5.98 s 是目前 13.18 s
裡最大的一塊，所以這件事本身是划算的下一步 —— 只是它不需要 Redis。

### 15.2 collector 的寫入路徑：Redis 不能移除那個寫入

索引和發現快取做完之後，一輪裡剩下的另一大塊是**每個鄰居一次 UPDATE**
（`last_seen`、`in_bps`/`out_bps`、計數器取樣）。Redis 不能讓這個寫入消失，
只能延後 —— 使用率是 UI 要顯示的東西，它總得寫在某個讀得到的地方。
真正的對照組不是「Postgres 對 Redis」，而是「一次一句」對「一句批次」：

| 做法 | 每次 | 一輪（10,324 列） |
|---|---|---|
| PostgreSQL UPDATE，一列一句 | 275.6 µs | 2.85 s |
| Redis SET，一次一個 round trip | 111.3 µs | 1.15 s |
| Redis SET，每 200 個一次 pipeline | 16.7 µs | 0.17 s |
| **PostgreSQL UPDATE，一句批次** | **15.4 µs** | **0.16 s** |

**批次化的 PostgreSQL UPDATE 和 pipeline 化的 Redis SET 一樣快（15.4 µs
對 16.7 µs）。** 既然如此，用 Redis 換來的不是速度，是多一個有狀態元件、
多一個真相來源、多一條重開機後要對帳的路徑。**不要。**

### 15.3 API 的讀取路徑：這裡才有道理

| 做法 | 時間 |
|---|---|
| 從 PostgreSQL 重建整張拓樸圖（1000 節點 / 1426 條線 / 731 KiB JSON） | 49.0 ms |
| 從 Redis 取同一份答案（含 `json.loads`） | 7.5 ms |

拓樸圖**每 300 秒才變一次**，但每個開著頁面的瀏覽器每次請求都在重建它。
這是唯一一個教科書級的快取場景。不過要誠實：49 ms 不是什麼急症，
而且如果直接把 JSON 當 blob 回傳（不在 API 端 `json.loads` 再 dump），
那 7.5 ms 還會再降一個數量級。值得做，但它是優化，不是救火。

### 15.4 分片之後：這裡也有道理

第 13.4 節的 `DiscoveryCache` 是**行程內**的。第 11 節第 5 項（collector
行程分片）一旦做下去，N 個行程會各自保有一份，於是同一個新鄰居會被 N 個
行程各自解析 DNS、各自 SNMP 探測、各自嘗試 insert（`IntegrityError` 已經
接住了，但工作是重複的）。`claim()` / dead-end 這組狀態本質上就是
「跨行程的鎖 + TTL 快取」，資料量極小 —— 這正是 Redis 存在的理由。

同樣地，`OfflineBackoff` 也是行程內的（第 5 節有說明為什麼刻意如此）。
分片之後如果希望「某台設備掛了，所有行程都知道」，那也是 Redis 的位置。

### 15.5 結論

| 位置 | 要不要 Redis | 理由 |
|---|---|---|
| collector 讀 `raw_links` | **不要** | 快取的是自己寫的資料，行程內 dict 比 Redis 快三個數量級（15.1） |
| collector 每輪的寫入 | **不要** | 批次化的 Postgres UPDATE 和 pipeline 化的 Redis 一樣快（15.2） |
| API 的拓樸回應 | **要**，但是優化不是救火 | 每 300 秒才變一次卻每次請求重建（15.3） |
| 分片後的發現/退避狀態 | **要**，做了第 5 項才需要 | 跨行程的鎖與 TTL（15.4） |

一句話：**Redis 不該擺在資料庫前面當通用快取層。該擺在 API 後面當回應快取，
以及分片之後當行程之間的共享狀態。**

至於「資料庫快撐不住了所以要擋一層」這個前提 —— 以目前的數字還差得很遠：

| 設備數 | 資料庫每輪 | 佔 300 秒週期 |
|---|---|---|
| 500 | 13.78 s | 4.6% |
| 1000 | 26.12 s | 8.7% |

而且成長已經是線性的（14.3 節），所以照這條線外推，要到**大約 10,000 台**
才會把一個 300 秒的週期填滿。在那之前 PostgreSQL 都不是瓶頸，
而真正划算的下一步是 15.1 的行程內快取（省約 6 s/輪）和 15.2 的批次寫入
（省約 2.7 s/輪）—— 兩個都不需要新元件。

### 15.6 這一輪量測的侷限

- Redis 與 PostgreSQL 都在 loopback 上，沒有真實網路延遲。放到別的主機上，
  Redis 每次 round trip 會變貴（15.1 的結論只會更強），批次/pipeline 的
  做法受影響較小。
- 「PostgreSQL SELECT 579 µs」包含 SQLAlchemy ORM 建物件的成本，不是裸的
  資料庫延遲 —— 但這就是現在這份程式實際付的代價，所以用它比較是對的。
- 機隊模型裡匯聚與接取兩邊的鄰居對應刻意沒有做成完全對稱，所以
  `sum(total_bandwidth_mbps)` 改前改後的差（例如 500 台 11,350,000 →
  9,220,000 Mbps）不是乾淨的 2 倍。雙倍計算的修正是用第 13.5 節那個
  兩台交換機的端對端測試驗證的（2000 而不是 4000 Mbps）。

# 第三輪：把對照表收進記憶體、把寫入批次化，以及輪詢間隔到底是多少

## 17. 第 16 節的第 1、2 項

### 17.1 批次化之前還在發生的事

第 13 節加了索引之後，每條線路的查詢從全表掃描變成索引搜尋 —— 但**查詢次數
沒有變**。一輪裡每條線路仍然要：

```python
existing = await db.execute(select(RawLink).where(...))   # 找出這條線是哪一列
raw_link.last_seen = ...                                  # 改欄位 → 一句 UPDATE
```

500 台、10,324 條線 → **20,648 次往返**，外加每台設備的幾句。實測每輪 24,000
句 SQL。索引讓每一句變便宜，但便宜 20,648 次還是 20,648 次。

而這些查詢在問一個 collector 自己就知道答案的問題。`raw_links` 的對照表
（哪三個欄位對應哪一列）在一輪開始時就是確定的，而且 collector 是它的唯一
寫入者。

### 17.2 兩個改動

**對照表收進行程記憶體**（`app/core/link_index.py` 的 `RawLinkIndex`）：一輪
開始時用**一句** SELECT 把 `(local_device_id, local_port, remote_hostname) →
(id, 上一次的計數器取樣)` 全部讀進來，之後整輪都從 dict 回答。那 10,324 次
SELECT 直接消失。

**寫入批次化**（同檔案的 `LinkWriteBuffer`）：一台設備的線路不再一條一句
UPDATE，而是累積起來，最後發兩次 `executemany`（一次 UPDATE、一次 INSERT）。
驅動層怎麼送那些參數組（asyncpg 會用 prepared statement 加管線化）不在這裡
量測，但結果在下面。

為了讓 `executemany` 成立，每一列必須帶同樣的欄位，所以原本散在 ORM 物件上
的賦值被收斂成一個純函式 `traffic.sample_values()`，它接收「這一列現在是什麼」
和「這次量到什麼」，回傳「這一列應該變成什麼」。這也讓流量推導第一次可以單獨
測試（20 個邊界條件，見 17.5）。

### 17.3 實測（500 台、10,324 條線、真實 PostgreSQL 16.13）

同一支驅動，比較 `99d9e6b`（第二輪結束）與這一輪：

| COLLECTOR_CONCURRENT | 批次化之前 | 批次化之後 | 倍數 |
|---|---|---|---|
| 1 | 19.16 s | **4.25 s** | 4.5× |
| 10 | 13.16 s | **3.48 s** | 3.8× |
| 20 | 14.08 s | **3.82 s** | 3.7× |
| 40 | 14.54 s | **3.74 s** | 3.9× |

每輪的 SQL 敘述數：**24,000 → 3,853**（6.2 倍）。

兩邊的結果完全一致 —— `raw_links=10324`、`merged_links=922`、
`sum(total_bandwidth_mbps)=9220000` 三個數字在改前改後逐位相同，所以這 3.7 倍
不是少做事換來的。

第 16 節當時估「壓到 5 s 量級」，實際是 **3.8 s**，比估的好。

（同一設定重跑落在 3.1～3.8 s，約 ±10% 的變異。表格裡用的是改前改後成對跑的
那一組，因為只有成對的數字可以相減。）

### 17.4 連帶的結論：`COLLECTOR_CONCURRENT` 現在與資料庫無關了

| | 併發 1 → 40 |
|---|---|
| 第一輪（共用 session） | 完全無效 |
| 第二輪（每台一個 session） | 1.41× |
| 這一輪（批次化） | **1.14×（4.25 → 3.74 s）** |

這不是退步，是那一段變小了：每台設備的資料庫工作現在只有兩句敘述，併發能
重疊的東西幾乎不存在。**`COLLECTOR_CONCURRENT` 從此只是 SNMP 的旋鈕** ——
它控制同時有幾台設備在等 UDP 回應，資料庫那半邊已經不在乎。

### 17.5 一個刻意沒做的事：對照表不跨輪保留

第 16 節寫的是「留在行程記憶體裡」，實作是**每輪重讀一次**。差別是一輪一句
SELECT（約 50 ms，佔 3.8 s 的 1.3%），換掉的是一整類 bug：

API 在刪除設備時會連帶刪掉 `raw_links` 的列。跨輪保留的對照表會指向已經不
存在的列，而對不存在的列做 UPDATE **影響 0 列、不報錯** —— 那條線路就會從此
安靜地不再被記錄，直到行程重啟。拿 1.3% 換這個，不划算。

流量推導的 20 個邊界條件測試（`sample_values`）順便修掉一個一致性問題：
原本當某個埠對不到介面時，上一次的 `in_bps`/`out_bps` 會被**原封不動留在那裡**，
而那是一個不知道多久以前的速率。現在跟「關掉流量收集」走同一條規則 ——
容量與計數器取樣保留，速率清成 `null`。`null` 的意思是「沒量到」，它必須和
「沒流量」分得開。

### 17.6 成長形狀（1000 台，併發 20）

| 設備數 | raw links | 批次化之前 | 批次化之後 | 每條線（之後） |
|---|---|---|---|---|
| 250 | 5,324 | 7.52 s | **1.94 s** | 0.364 ms |
| 500 | 10,324 | 14.23 s | **3.77 s** | 0.365 ms |
| 1000 | 20,324 | 27.75 s | **6.29 s** | 0.309 ms |

每條線的成本依然是平的（0.364 → 0.309 ms，略降），成長指數 0.88 —— 固定開銷
隨規模攤薄。1000 台的資料庫時間是 300 秒週期的 **2.1%**。

照這個斜率，光看資料庫，要到**約 48,000 台**才會把一個 300 秒的週期填滿。
那早就過了 SNMP 迫使你分片的點（第 10 節），所以這條路到此為止 ——
資料庫已經不是這個系統裡值得再優化的東西了。

## 18. 輪詢間隔，以及告警能有多準

這份報告前面每一節都拿「300 秒週期」當分母，卻從來沒有把這個 300 秒當成一個
**參數**來檢討。它是 `COLLECTOR_INTERVAL`（`app/config.py`、`.env.example`、
`docs/CONFIGURATION.md`），預設 300 秒。這一節補上它真正的代價。

### 18.1 先修一個 bug：真正的取樣間隔不是 300 秒

```python
while True:
    await poll_all_devices()
    await asyncio.sleep(settings.collector_interval)   # 睡「整個」間隔
```

這是**在一輪跑完之後**才睡滿 300 秒，所以真實的取樣週期是
`間隔 + 一輪的時間`。500 台約 **350 秒**，1000 台約 **398 秒**，而且會隨機隊
大小、隨當下有幾台設備在等超時而漂移。

這不只是「數字不漂亮」。那個週期是**每一個 bps 的分母**，也是告警延遲的下限，
而設定檔裡的數字沒有告訴操作者任何一件事。

改成睡「剩下的時間」。實測（`COLLECTOR_INTERVAL=5`、一輪固定 2 秒）：

| | 每輪起點的間隔 |
|---|---|
| 改前 | 7.01, 7.01, 7.00 s |
| 改後 | **5.00, 5.00, 5.00 s** |

一輪跑超過間隔時會記一行 warning 並且留 5 秒喘息，不會變成對資料庫和每一台
交換機的 hot loop。

### 18.2 告警延遲的實際帳（500 台、間隔 300 秒、一輪 50 秒）

告警只在**一輪的最後**評估（所有設備輪完 → 合併 → `run_check_cycle()`），
所以每一種告警都要加上「等這一輪跑完」。

**設備／線路斷線：**

| 組成 | 時間 |
|---|---|
| 等到這台設備的輪詢順位 | 0 – 300 s |
| 那次失敗的輪詢本身（`SNMP_TIMEOUT=5` × `1+SNMP_RETRIES=2`） | 15 s |
| 等剩下的設備輪完 + 合併 + 告警 | 0 – 50 s |
| **合計** | **15 – 365 s，平均約 190 s** |

**線路使用率 —— 這裡比延遲更嚴重：**

計數器推導出來的 bps 是**整個間隔的平均值**，不是當下的速率。所以：

> 能讓 70% 門檻被跨過的**最短事件**＝ 門檻 × 間隔 ＝ 0.70 × 300 ＝ **210 秒的滿線速流量**。

比 210 秒短的爆量，無論多滿，**永遠不會觸發告警** —— 一個 30 秒打滿 1G 的
事件在 300 秒的窗裡只有 10%。這不是延遲問題，是量測本身被低通濾掉了，
而任何用計數器輪詢的系統都一樣。

至於延遲：一條線路從滿載開始算，

| | 時間 |
|---|---|
| 平均（1.2 × 間隔 + 半輪） | **約 385 s（6.4 分）** |
| 最差（1.7 × 間隔 + 一輪） | **約 560 s（9.3 分）** |

所以「告警發生在事件五分鐘後」這個描述是對的，而且還偏樂觀。

### 18.3 那為什麼不直接把間隔調小

因為間隔的下限不是資料庫，是 **SNMP 解碼的 CPU**。一輪的成本（500 台約 50 s）
和間隔無關，所以縮短間隔等於直接放大佔用：

| COLLECTOR_INTERVAL | 能觸發 70% 的最短事件 | 飽和事件平均延遲 | 500 台的 CPU 佔用 |
|---|---|---|---|
| 300 s（現況） | 210 s | 6.4 min | **17%** |
| 120 s | 84 s | 2.8 min | **42%** |
| 60 s | 42 s | 1.6 min | **83%** |
| 30 s | 21 s | 1.0 min | **166%（跟不上）** |

單一行程在 500 台可以撐到 **120 秒**，還有餘裕吸收斷線設備的超時。60 秒要兩
個分片，30 秒要四個 —— 這些數字是第 17.4 節的直接結果：資料庫已經不在等式
裡了，分母完全由 SNMP 決定。

而且還有一個不在這台機器上的成本：**每台設備每輪被走訪 17 張表**。
把間隔從 300 秒調到 30 秒，等於要求每一台接取交換機的 SNMP agent（在控制平面
上優先權很低的那個行程）承受 10 倍的查詢。通常是這一點先出問題，不是 collector。

### 18.4 真正能解決的做法：把迴圈按用途拆開

現在一輪做兩件完全不同週期的事：**接線盤點**（LLDP/CDP 表、埠對照、自動發現）
變動極慢，**存活與流量**（ifOperStatus、兩個 octet 計數器）需要很快。
把它們綁在同一個間隔上，就是用最慢那件事的成本去買最快那件事的頻率。

拆開之後，快迴圈不需要走訪任何整張表 —— collector 已經把每條線路的
`local_port_index` 存在 `raw_links` 裡了，**它確切知道哪些 ifIndex 有接線**。

| | 現在的完整一輪 | 快迴圈（只查有接線的埠） |
|---|---|---|
| 每台設備的 varbind | 約 500+ | 約 62（20.6 條線 × 3 個 OID） |
| 每台設備的 PDU 往返 | 約 40 | 約 3 |

**估**（不是實測，由 varbind 數推算；第 20.3 節實測是 **1/5**）：
快迴圈的解碼成本約是完整一輪的 1/8，
所以 500 台、60 秒的快迴圈約佔 10%；配一個 300 秒的慢迴圈（17%），
合計約 27% —— 比現在單一 60 秒迴圈的 83% 便宜得多，而使用率告警的延遲進到
**1.6 分鐘**、最短可偵測事件進到 **42 秒**。`run_check_cycle()` 要搬到快迴圈上，
否則告警還是跟著慢迴圈走。

至於斷線，輪詢永遠贏不了間隔。要**秒級**只有一條路：收 **SNMP trap**
（udp/162 的 linkDown/linkUp），延遲是毫秒級而不是分鐘級。流量沒有對應的
trap，要秒級得靠設備端的 RMON alarm 或 sFlow／streaming telemetry ——
那是另一個專案的範圍。

### 18.5 順手修掉兩個告警 bug

這兩個都是第 13 節的直接後果：使用率從「永遠是 0」變成真實數值之後，
原本不可能走到的程式碼路徑第一次可以走到。

`check_link_utilization()` 原本這樣取值：

```python
max_util = max(link.utilization_in_percent or 0, link.utilization_out_percent or 0)
```

第 13 節讓使用率可以是 `null`（沒量到）之後，這個 `or 0` 就變成了一個
**假恢復**：一條線路正在高使用率告警中，只要有一輪沒量到（collector 剛重啟、
計數器被清掉、埠對不到介面），它就會被當成 0% 而**自動解除告警**。

改成「沒有任何一個方向量到 → 這一輪不碰這條線路的告警狀態」。
`null` 的意思是「不知道」，不是「沒事」。

**第二個更嚴重：使用率告警根本解除不了。** `_resolve_alert()` 用字串替換去
反推「這個恢復事件要關掉哪一個告警」：

```python
high_type = event.alert_type.value.replace("_normal", "_high")
```

`cpu_normal` → `cpu_high` 可以，`memory_normal` → `memory_high` 可以，
但 `link_utilization_normal` → `link_utilization_high` —— 而列舉裡叫
`link_high_utilization`。所以 `AlertType("link_utilization_high")` 會丟
`ValueError`，而 `run_check_cycle()` 沒有接，整個告警階段當場中斷。

也就是說：一條線路的使用率降回門檻以下的那一輪，**告警階段會整輪失敗**，
而且每一輪都會再失敗一次，直到使用率又升回去。在使用率永遠是 0 的時候這段
程式永遠走不到；接上真實流量之後它就在等著。

改成明確的對照表（`AlertEngine.RECOVERY_CLOSES`），並且對照不到時記 error
而不是丟例外。四條恢復路徑（device、cpu、memory、link）都用真實的 AlertEngine
跑過：觸發 → 沒量到的一輪（告警必須存活）→ 真實的低值（必須解除）。

# 第四輪：把迴圈按用途拆開，並接上 trap

第 19 節的第 1、2 項。這一輪的主題不是「跑得更快」，是**告警的可信度**：
一個在事件五分鐘後才出現的告警沒有用，而上一輪已經證明那不是誇飾
（斷線平均 190 秒，使用率平均 385 秒）。

## 20. 快慢迴圈拆開

一輪原本同時做兩件週期完全不同的事：

| | 怎麼問 | 多久變一次 |
|---|---|---|
| **盤點**：誰接到誰、埠速、新設備 | 走訪 17 張表、約 500 個 varbind | 有人動線才變 |
| **存活 / 線路狀態 / 流量** | 每條線 3 個值 | 每秒都在變 |

綁在同一個間隔上，就是用最慢那件事的成本去買最快那件事的頻率。

### 20.1 先決條件：`SnmpEngine` 不能一台一個

原本的寫法是每台設備建一個 `SNMPCollector`，也就是一個 `SnmpEngine`，
用完就關。那是上一輪之前「每次請求都建一個」的改良版，但還是太貴：

```
建一個 SnmpEngine：約 36 ms 的 CPU，每一次都是，沒有攤提
```

pysnmp 會為每一個 engine 重新讀取並編譯它內建的 MIB 模組。500 台就是
**一輪 18 秒的純 CPU**，花在送出第一個封包之前。300 秒一輪勉強吞得下，
60 秒一輪吞不下。

engine 裡沒有一樣東西是「這台設備的」—— UDP socket、MIB 機制、request id
空間都不是。**是「憑證」才是**。所以改成依憑證（community／v3 使用者）
共用一個 collector，整個機隊通常只需要一到數個 engine
（`app/core/snmp_pool.py`）。

要共用就要先確認兩件事，兩件都實測過：

* **不會串線。** 一個 engine、兩個模擬 agent、200 次交錯請求，
  每一次回來的都是該位址自己的答案（0/200 不符）。pysnmp 用 request id
  與來源位址做解多工，這本來就是它的設計。
* **每次輪詢的表快取不會互相污染。** `SNMPCollector` 在一次 `poll_device()`
  內會快取 `ifDescr`／`ifName`，原本在輪詢結束時整個清掉 —— 共用之後那會
  把另一台還在輪詢中的設備的表也清掉。改成**依位址計數**，誰輪完清誰的。

超過上限（預設 16 種憑證）的部分退回舊行為（自己一個 engine，用完關掉），
所以一個有幾百種 community 的機隊不會把記憶體吃光。

### 20.2 兩個迴圈各自做什麼

快迴圈**不走訪任何整張表**。盤點那一輪已經把每條線的 ifIndex 存在
`raw_links.local_port_index` 裡了，所以它確切知道要問哪幾個埠：

| | 盤點一輪 | 快迴圈 |
|---|---|---|
| 每台的 varbind | 約 500 | 61（sysUptime + 20 條線 × 3） |
| 每台的 PDU | 約 40 | 3 |

快迴圈**刻意不做**的事：

* **CPU／記憶體。** 廠商的那些 OID 本身就是五分鐘平均值
  （`cpuUsage5min` 之類），每分鐘問一次只會增加負載，不會增加資訊。
* **ifHighSpeed。** 埠的容量是盤點：它在有人改設定時才變，不會在流量流動
  的時候變。
* **任何 `raw_links` 的盤點欄位。** 兩個迴圈擁有**不相交的欄位集合**
  （`app/core/link_index.py`），這是它們可以同時跑而不互相覆蓋的原因。

反過來，**告警檢查搬到快迴圈上**。告警再新也不會比評估它的那個迴圈新，
把 `run_check_cycle()` 留在 300 秒的迴圈上，前面做的一切都是白做。
使用率讀的是 `merged_links`，所以合併也一起搬過來。

還有一個順手的收穫：快迴圈負責取樣計數器之後，盤點那一輪就不必再走訪
`ifHCInOctets`／`ifHCOutOctets` 了 —— 17 張表少 2 張。

### 20.3 實測：SNMP 那一半

100 台設備、併發 20、4 個 snmpsim agent（48 個介面、20 條線）。
量的是**這個行程的 CPU 時間**：模擬器在 loopback 上用微秒回答，真實交換機
用毫秒，所以 wall time 在這裡沒有意義，而「一輪佔間隔的百分之幾」要的本來
就是 CPU。

| | 每台的 CPU | 500 台一輪 |
|---|---|---|
| 盤點，每台一個 engine（改前） | 227.5 ms | 114 s |
| 盤點，共用 engine（這一輪） | **65.3 ms** | **32.7 s** |
| 快迴圈，共用 engine | **13.0 ms** | **6.5 s** |

* engine 共用讓盤點那一輪省下 **162 ms／台**，是 3.5 倍。
  （孤立測量時建一個 engine 是 36 ms；在實際負載下省下來的是 162 ms，
  因為還有關閉、以及 20 個同時存在的 engine 造成的配置與 GC 壓力。）
* **快迴圈是盤點一輪的 1/5.0**（第 18.4 節估 1/8，實際 1/5）。

### 20.4 一半的 CPU 花在重新解析同樣的 OID

快迴圈第一次量出來是 20.9 ms／台，比估的貴。追下去發現：

```
把 61 個 OID 解析成 pysnmp 的請求物件：10.44 ms
同樣 61 個，已經解析過的：          0.01 ms
```

pysnmp 在送出每一個請求之前，會把每一個 OID 對它內建的 MIB 解析一次。
而快迴圈每一輪問的是**完全一樣的 OID**。把解析過的請求物件留著重用之後：

| 每個 GET 幾個 varbind | 每台 PDU 數 | 改前 | 改後 |
|---|---|---|---|
| 4 | 16 | 32.3 ms | 24.8 ms |
| 8 | 8 | 25.0 ms | 19.6 ms |
| 16 | 4 | 22.0 ms | 11.2 ms |
| **24（現在用的）** | **3** | 20.9 ms | **11.1 ms** |
| 32 | 2 | 20.0 ms | 9.8 ms |
| 61 | 1 | 22.3 ms | 9.4 ms |

順帶回答了「要不要把 61 個 varbind 塞進一個 PDU」：成本幾乎全在
**每個 varbind**（約 0.15 ms），不在每個請求（約 1 ms）。塞成一個請求只省
1.7 ms／台，卻要賭對面的 agent 不會回 tooBig。維持 24。

### 20.5 資料庫那一半（500 台、10,324 條線、真實 PostgreSQL 16.13）

| | 每輪 | 敘述數 |
|---|---|---|
| 盤點一輪 | **1.60 s** | 1,503 |
| 快迴圈一輪 | **0.85 s** | **14** |
| └ 其中合併 | 0.18 s | 4 |
| └ 其中告警 | 0.05 s | 6 |

盤點那一輪從第三輪的 3.8 s 降到 1.60 s，是因為合併與告警搬走了、
而且不再寫流量欄位。

結果逐位相同：`raw_links=10324`、`merged_links=922`、
`sum(total_bandwidth_mbps)=9220000` —— 和第 17.3 節一樣，所以這些數字不是
少做事換來的。另外 10,324 條線全部都有速率，491 條 down 的線產生了 491 個
`link_down` 告警。

### 20.6 告警階段的兩個 N+1：2,349 句 → 6 句

把告警搬到 60 秒的迴圈上，等於把它的成本乘以五，所以先看了一眼它在做什麼：

| | 每輪敘述數 | 每輪時間 |
|---|---|---|
| 原本 | 2,349 | 1.44 s |
| 查過一次的告警收進記憶體 | 928 | 0.56 s |
| 連設備也是（`_get_device`） | **6** | **0.05 s** |

兩個都是同一個形狀的問題，和第 8 節、第 17 節一樣：
「這個東西有沒有已經在告警了？」每台設備問三次、每條合併線路問一次、
每條線問一次 —— 全部是分開的 SELECT。一輪開始時一句
`SELECT ... WHERE is_active` 把它們全部讀進來，之後都是字典查詢。
`check_link_utilization()` 為了拿門檻而對每條合併線路查一次設備，也是同一件事。

### 20.7 500 台的新帳

| | 第三輪（只有 300 秒迴圈） | 這一輪 |
|---|---|---|
| 盤點 SNMP | 114 s | **32.7 s** |
| 盤點 資料庫 | 3.8 s | **1.60 s** |
| 快迴圈（每 60 秒） | — | 6.5 s + 0.85 s |
| **300 秒內的 CPU 合計** | 118 s | **34.3 + 5 × 7.4 = 71 s** |
| **佔用** | 39% | **24%** |

（第 7 節與第 17.7 節的 46 s／50 s 是另一套量測環境的數字，不能和這一欄
直接相減；這張表從頭到尾用同一套量測環境，只有欄與欄之間可以比。）

對照一下「不拆迴圈，直接把間隔調到 60 秒」這個選項：
一輪 32.7 s，每 60 秒一次 = **55%**。拆開之後拿到同樣的告警頻率，只要 24%。

### 20.8 告警延遲的新帳

| | 第三輪（300 秒） | 這一輪（快迴圈 60 秒） |
|---|---|---|
| 設備斷線 | 15 – 365 s，平均 190 s | **15 – 80 s，平均約 45 s** |
| 使用率：能觸發 70% 的最短事件 | 210 s | **42 s** |
| 使用率：飽和線路的平均延遲 | 385 s（6.4 分） | **76 s（1.3 分）** |
| 使用率：最差 | 560 s（9.3 分） | **110 s（1.8 分）** |
| 單一線路 up/down | 沒有這個告警 | **毫秒（trap）或 ≤ 60 s（輪詢）** |

斷線那 15 秒是 `SNMP_TIMEOUT=5` × `1+SNMP_RETRIES=2`，那是物理下限，
不是程式的問題 —— 真的要再快只能靠 trap，而那正是下一節。

### 20.9 固定節奏，兩個迴圈各自算各自的

第 18.1 節把「睡整個間隔」改成「睡剩下的時間」。兩個迴圈都用同一個函式
（`_fixed_cadence`），實測（間隔 6 秒／一輪 1 秒，與間隔 2 秒／一輪 0.4 秒，
同時跑）：

```
盤點迴圈每輪起點間隔：6.00, 6.00
快迴圈每輪起點間隔：  2.00, 2.00, 2.00, 2.00, 2.00, 2.00
```

一輪跑超過自己的間隔時記一行 warning，並留 5 秒喘息再跑下一輪，
不會變成對資料庫和每一台交換機的 hot loop。

## 21. SNMP trap 接收器

輪詢永遠贏不了自己的間隔。即使是快迴圈，一個埠斷掉也要等它下一次問到。
trap 是設備在事件發生的當下主動說，而且告警是**從 trap 直接發出來**的，
不是等下一輪。

### 21.1 收到之後做什麼

1. 來源位址對照受管設備的管理位址（快取 60 秒，查不到時最多 5 秒重讀一次）。
   不是受管設備 → 丟掉，每個來源只記一次 warning。
2. community 由 pysnmp 驗（v1／v2c）。v3 notification 不支援 —— 那需要
   每台設備的 engine id 與 USM 使用者，是另一套設定面。
3. `linkDown`／`linkUp` 以外的都不處理（`coldStart`／`warmStart` 只記一行：
   計數器重置本來就會讓速率推不出來，見 `app/core/traffic.py`）。
4. 從 varbind 取 ifIndex 與 ifOperStatus。設備送的形狀差很多 —— 有的只送
   ifIndex、有的把 index 放在 OID 的尾巴而不是值裡、有的連 ifOperStatus
   都不送（那就用 trap 的種類推定）——  三種都讀。
5. 那個埠上**有線**才動作：接筆電的埠斷掉不是這個專案的事。
6. 寫 `raw_links.oper_status`，然後只對**那幾條線**跑一次告警評估。

收封包的 callback 是同步的、跑在 event loop 上，所以它只做解析和入佇列；
碰資料庫的事都在一個 asyncio 工作者裡，一次處理一批。佇列有上限
（2000），滿了就丟並計數 —— 一個 chassis 重開機會每個埠送一個 trap，
佇列不能漲到把 collector 撐死。丟掉的代價是延遲，不是正確性。

### 21.2 實測

真的從 UDP 送進去的 trap，一路到資料庫裡出現告警：

| | |
|---|---|
| linkDown → 告警存在 | **40 ms** |
| linkUp → 告警解除 | **21 ms** |
| 300 個 trap 的風暴 | 最後一個送出後 **0.02 s** 排空，0 個被丟棄 |
| community 不對 | 根本沒進到 handler |
| 來源不是受管設備 | 丟掉，記一次 warning |
| 那個埠上沒有線 | 不動作 |
| 綁不到那個埠（已被占用／沒權限） | 記 error，collector 照常跑 |

（40 ms 裡面有 10 ms 是測試自己的輪詢間隔。）

### 21.3 trap 不是事實來源

一個 trap 是一個沒有確認的 UDP 封包：可能遺失、重複、延遲、偽造。
所以整個設計讓 trap 只能是**比較早的答案**，不能是唯一的答案：

* trap 寫的是快迴圈也在寫的同一個 `oper_status` 欄位，所以下一次快迴圈會
  重新確認。**遺失一個 trap 的代價是一個快迴圈的延遲；偽造一個 trap 的
  效果最多維持一個快迴圈。**
* 只有來源是受管設備、community 正確、而且那個埠上有線的 trap 會被採用。
* 預設關閉。它要開一個監聽埠、要能綁 1024 以下的埠，而且在設備端設好
  trap 目的地之前什麼都收不到。

流量沒有對應的 trap —— 沒有「我的計數器剛剛跳起來」這種通知。要比間隔更
細的流量告警，只能靠設備端的 RMON alarm、sFlow 或 streaming telemetry。

### 21.4 一個實務上的細節

設備斷線時**它自己不會送 trap**（它死了）。送 trap 的是它的鄰居 ——
每一條朝向它的線都會送一個 linkDown。所以實際上會先在毫秒內看到
「這幾條線斷了」（可以直接派人去看的資訊），然後在 80 秒內才補上
`device_offline`。這個順序是對的。

### 21.5 它要求設備從管理位址送 trap（已解決，見第 37 節）

> 這一節寫的是第四輪當時的狀態。第 37 節把它修掉了：現在比對的是設備
> **所有已知的位址**，所以下面說的那個「每台都要加一行」不再需要。

認設備是用**來源位址**對 `devices.ip_address`，而這在既有環境裡有一個不
明顯的維運代價：不少平台預設是用**出口介面**的位址送 trap，而那不一定是
你拿來管理它的那個位址。對不上的 trap 會被丟掉（每個來源記一次 warning），
症狀是「開了 trap 但什麼都沒發生」。

要修的話是在設備端指定 trap 來源（Cisco IOS 的 `snmp-server trap-source`、
NX-OS 的 `snmp-server source-interface traps`、Junos 的
`set snmp trap-options source-address`）—— 也就是**每一台都要加一行**，而
大家通常指到 loopback。這是這個題目裡唯一會逼出「要不要在所有設備上加
loopback」的地方。

它是這份實作的選擇，不是 SNMP 的要求。比對「那台設備所有已知的位址」就不
需要那一行：

| 位址來源 | 從哪裡拿 | 成本 |
|---|---|---|
| v1 trap 的 agent-address 欄位 | trap 封包自己帶 | 零，封包裡已經有了 |
| LLDP 管理位址 | 盤點迴圈已經在讀（`lldpRemManAddrTable`） | 零，已經在記憶體裡 |
| 設備自己的介面位址 | 多走訪一次 `ipAddressIfIndex`，每台幾列 | 盤點迴圈多一次小走訪，要一張 `device_addresses` |

前兩個幾乎免費，第三個才是真正能涵蓋所有情況的那個。

**做了，見第 37 節**：最後採用的是第三項加第一項（LLDP 管理位址是多餘的 ——
那個位址本來就在設備自己的位址表裡），量到的代價是每台設備盤點輪詢多 10%
的 CPU。現在的做法與操作者還需要自己處理的情況寫在
[docs/CONFIGURATION.md](CONFIGURATION.md) 第 5.3 節，判讀 `Traps:` 那一行
的方式在 5.4 節。

## 22. 這一輪的侷限

* SNMP 那一半是對 loopback 上的 snmpsim 量的。真實交換機的 agent 慢得多，
  但那是**對方的**時間，不是這個行程的 CPU，而這一節的佔用算的是後者。
  反過來說，wall time 的數字在這裡沒有參考價值。
* 100 台外推到 500 台。第 17.6 節已經驗過資料庫那一半是線性的；SNMP 那一半
  每台之間沒有共用狀態（engine 除外，而那正是被攤提的東西），所以線性是
  合理的，但沒有實測 500 台的 SNMP。
* 同一組設定重跑的變異約 ±10%（盤點每台 65.3 與 77.9 ms 兩次）。表格裡用的
  都是同一次跑出來的成對數字。
* 兩個迴圈同時寫同一張表的競爭沒有在高負載下實測。它們寫的欄位不相交，
  而且所有批次寫入都依主鍵排序後才送（避免互相死鎖），但這是設計保證，
  不是實測結果。
* trap 的量測是在同一台機器上送收的。真實環境還要加上網路延遲 ——
  那仍然是毫秒等級。

# 第五輪：把機群拆給多個行程

## 24. 分片

第 10 節的結論是：一輪的瓶頸是 **SNMP 解碼的 CPU**（實測佔 77%），不是等
交換機回應。那代表 GIL 讓多執行緒幫不上忙，但也代表一件好事 —— 一輪裡沒有
任何一台設備需要跟另一台在同一個行程裡：每台各自輪詢、各自寫入。所以跨過
單核上限的方法是**多開行程**，每個負責機群的一部分。

### 24.1 分片鍵為什麼是 `devices.id % N`

```python
# app/core/sharding.py
def criterion(self, column):
    return column % self.count == self.index
```

三個性質，而這是同時具備三個的最便宜寫法：

1. **穩定。** 一台設備屬於哪一片只取決於它自己的 id，所以增刪**別的**設備
   永遠不會把它搬走。如果用「排序後每 N 筆取一筆」，刪掉一台就會讓整個
   機群重新洗牌，而每一台被搬走的設備都會失去它的離線退避狀態與輪詢節奏。
2. **能下到 SQL 裡。** 條件寫在 WHERE 裡，所以一片只讀自己的設備與自己的
   線路 —— 500 台 10,000 條線、四片的話每個行程只讀四分之一，而不是全部
   讀進來再丟掉四分之三。用 hostname 的 hash 理論上更平均，但那算不進
   查詢裡；而自動遞增的 id 對任何數取模本來就是平均的（實測 1000 個 id、
   2/3/4/8 片，最大與最小片的差距都在 1% 以內）。
3. **完整且互斥。** 每個 id 剛好屬於一片。這是離線退避與每台設備的節奏
   不需要任何跨行程協調的原因：每台設備剛好有一個主人。

`Shard(1, 0)` 刻意不是特例：`owns()` 永遠為真、`criterion()` 回傳 None，
所以單一行程產生的 SQL 跟沒有分片這個功能時**完全一樣**（第 25 節的回歸
測試就是驗這件事）。

### 24.2 分不掉的那一段

一輪裡有兩件事不是「關於一台設備」，而是「關於整個機群」：

* `TopologyEngine.update_merged_links_in_db()` 讀所有 raw_links 然後整張
  重建 merged_links。N 個行程同時做，會各自刪掉別人剛寫的列。
* `AlertEngine.run_check_cycle()` 讀所有設備與所有合併線路。N 個行程同時做
  會把同一組門檻算 N 次，而且因為「這個東西有沒有已經在告警了？」是
  SELECT 之後接 INSERT，競爭的結果是**重複的告警**，不是一筆。

所以這一段由**一個**行程做，靠搶一個 lease 決定是哪一個：一列有 owner 與
到期時間的資料。持有者每輪續約；持有者死了，那一列過期，下一個來問的人
接手。設計上刻意不是「固定 0 號做」—— 0 號掛掉就等於整個機群沒有告警。

### 24.3 lease 放在資料庫，而且時鐘必須是資料庫的

**為什麼不是 Redis：** 沒有資料庫 collector 本來就一件事都做不了，所以把
lease 放在那裡不增加任何新的故障模式。放在 Redis 就多一種故障：Redis 掛了
的時候每台設備都還在正常輪詢，但沒有人在算告警。這跟第 15.5 節對快取的
結論是同一個判斷。代價是每輪每片一句 UPDATE，實測 **1.77 ms**。

**時鐘：** 兩台主機的時鐘差一分鐘，就會對「這個 lease 還活著嗎」給出不同
答案，然後兩個行程一起做整機群的工作。所以這裡寫進去的每一個到期時間、
以及每一次跟它的比較，都在資料庫裡算完：

```sql
UPDATE collector_leases SET owner = :owner,
       expires_at = now() + interval '180 seconds', ...
 WHERE name = 'fleet-wide' AND (owner = :owner OR expires_at <= now())
```

續約與接手是**同一句**，所以持有者不需要先放掉再拿，中間沒有空窗。
rowcount 是 1 就是拿到了。SQLite 用 `datetime('now', '+180 seconds')`，
其他方言退回行程自己的時鐘並記一行 warning（第 25 節兩個方言都測了）。

TTL 是續約間隔的三倍（快迴圈 60 秒 → 180 秒）。一倍會讓跑久一點的那一輪
弄丟自己正在用的 lease；更長則是持有者死掉之後多空更久。owner 名字是
`shard-<i>-of-<N>`，不是隨機值 —— 所以一個行程重啟之後**續約的是自己原本
那一個**，不必等它過期。

### 24.4 實測：同一個 400 台機群，1 / 2 / 4 個行程

400 台設備（8,000 條線）分佈在四個真實 snmpsim agent 上，一個 PostgreSQL，
量的是**每個行程自己的 CPU 時間**（loopback 上的 wall time 沒有意義，
理由見第 22 節）。所有分片同時啟動，這也是它們實際跑的方式。

| 行程數 | 每片的設備 | 盤點一輪 CPU（最忙的那片） | 快迴圈一輪 CPU | 加速 | 每台 |
|---|---|---|---|---|---|
| 1 | 400 | **26.18 s** | 5.49 s | 1.00× | 65.5 ms |
| 2 | 200 | **14.05 s** | 2.69 s | **1.86×** | 70.2 ms |
| 4 | 100 | **8.58 s** | 1.69 s | **3.05×** | 85.8 ms |

那個 65.5 ms/台 值得停一下：第 20.2 節用完全不同的方式（100 台、成對 A/B、
只量 SNMP 層）量到共用 engine 之後是 **65.3 ms/台**。兩個數字差 0.3%，
所以第 20.7 節把 100 台外推到 500 台的那一步，現在有 400 台的直接佐證。

### 24.5 不會隨行程數變小的那些成本

加速不是 2× 和 4×，而是 1.86× 和 3.05×。把全部分片的 CPU 加起來就看得到
代價：

| 行程數 | 全部分片的 CPU 合計 | 相對單一行程 |
|---|---|---|
| 1 | 26.18 s | — |
| 2 | 27.94 s | +6.7% |
| 4 | 33.20 s | **+26.8%** |

拆成兩個來源：

* **主機競爭。** 同一片單獨跑（沒有兄弟行程）是 **7.97 s**，四片一起跑是
  8.58 s —— 差 7.6%。這台量測機只有 4 核，而且四個模擬 agent 也在上面跑；
  真實部署的交換機在別的地方。
* **每個行程各自的固定成本。** 剩下的部分。自動發現的「我已經知道哪些
  設備？」那一句是**整個機群**的（不能分片，否則每一片都會把別片的設備
  當成新鄰居重新加一次），所以 N 個行程各讀一次；另外每個行程各有自己的
  event loop、自己的 engine、自己的連線池。

所以誠實的說法是：**分片把每個行程的工作除以 N，但整台主機要多付
7%（兩片）到 27%（四片）。** 想要的是前者 —— 單核的上限才是問題。

### 24.6 500 台與 1000 台的新帳

用 24.4 量到的「每台成本」外推（每片 125 台時用 100 台/片 量到的
85.8 ms/台，所以四片那一欄是偏保守的）：

| 500 台 | 一片 | 兩片 | 四片 |
|---|---|---|---|
| 盤點一輪 CPU（每片） | 32.8 s | **17.6 s** | **10.7 s** |
| 快迴圈一輪 CPU（每片） | 6.9 s | **3.4 s** | **2.1 s** |
| 300 秒內的 CPU（每片） | 67 s | **35 s** | **21 s** |
| **佔用（每片）** | 22% | **12%** | **7%** |

（22% 與第 20.7 節的 24% 是同一件事重量一次，差在量測環境與這一輪用
400 台直接量到的每台成本。）

最後一欄是重點：**1000 台用四片，等於 500 台用兩片。**
每片 250 台 × 70.2 ms = 17.6 s 盤點、3.4 s 快迴圈 → 每片 12%。
原本的設計前提是「500+ 台」，現在往上一個數量級是改設定，不是改架構。

反過來看「間隔還能壓多短」。讓一片維持在半個核以內：

| 行程數 | 能撐的最短快迴圈間隔 |
|---|---|
| 1 | 17.6 s |
| 2 | 7.7 s |
| 4 | 4.5 s |

但到這裡 collector 已經不是限制了，限制變成**對面**：每台設備每輪被問
3 個 PDU，而斷線偵測的下限是 `SNMP_TIMEOUT × (1 + SNMP_RETRIES)` = 15 秒
（第 20.8 節）。真正要再快只能靠 trap，而 trap 已經在第 21 節做掉了。

分不掉的那一段的成本，在 500 台的真 PostgreSQL 上量（第 17 節的環境）：
合併線路 **0.21–0.26 s／4 句**，告警檢查 **0.04–0.06 s／5 句**。
也就是每 60 秒 0.3 秒落在一個行程上 —— 不管幾片，約半個百分點的核。
它不是瓶頸，所以沒有必要把它也拆開。

### 24.7 第 23 節第 3 項：三件事裡有兩件不需要共享儲存

第 23 節第 3 項寫的是「分片後把發現狀態、離線退避、trap 接收搬到共享儲存
（Redis）」。做下去之後，三件事只剩一件是真的：

| | 要不要共享狀態 | 為什麼 |
|---|---|---|
| 離線退避 | **不用** | 分片鍵讓每台設備剛好有一個主人，退避狀態本來就只有一個行程在算。改變片數時那些狀態會重算，代價是每台設備多一輪探測。 |
| trap 接收 | **不用** | 一台主機的 udp/162 只有一個行程綁得到，綁到的那個就是唯一的接收者。它查設備是用來源位址對整個 `devices` 表，所以它處理整個機群的 trap —— 不是只有自己那一片。實測：對**別片**的設備送 linkDown，49 ms 後那條線的狀態變了，4 ms 後告警出現；linkUp 26 ms 解除。 |
| 自動發現 | **會重複，但有界** | 「我已經在處理這個鄰居了嗎？」是行程內的答案。 |

第三項值得講清楚，因為它是唯一真的重複的地方。重複只發生在**同一個新鄰居
同時被不同片的設備看到**的時候：一支電話只掛在一台交換機的一個埠上，
所以它只會被一片看到；會重複的是「兩條上行接到不同片的交換機」那種鄰居。

端到端量過一次（第 25 節的 `e2e_discovery.py`）：一台未登錄的交換機同時
掛在兩片各一台設備上，兩片在同一輪都看到它。結果是**一列設備**（輸的那
一邊撞到 hostname 的 unique，`IntegrityError` 本來就接住了），而重複的
工作是**一次 DNS 查詢與一次 SNMP 探測**。從下一輪開始，整機群的 seed
查詢讓兩片都知道這台設備，兩邊都不會再探測。

所以結論是**不做**：為了一次探測去換一個 Redis 依賴不划算。要盯的話，
每片的 log 每輪都印 `discovery cache: {... 'dead_ends': N}` —— 那個數字
就是這一片正在壓住多少個「轉不成設備的鄰居」，也是重複的上限。

### 24.8 故障模式

**少跑一片。** `COLLECTOR_SHARDS=4` 但只起三個行程，那四分之一的設備就
沒有人輪詢，而唯一的症狀是它們慢慢開始報 `device_offline` —— 看起來像
網路有問題，不像 collector 沒開。所以每片每輪會續約一列自己的
`member-<n>`，而拿到 fleet-wide lease 的那個行程會讀它們：

```
WARNING - Shard(s) 1 of 2 are not reporting: about 50% of the fleet is not
being polled by anyone. Start them, or lower COLLECTOR_SHARDS on every
process to the number you run.
```

狀態有變化就報，之後每 10 輪才報一次 —— 一片掛掉會掛一陣子，每分鐘一行
只會把其他東西淹掉。

**持有者掛掉。** 實測（快迴圈 4 秒、TTL 30 秒）：`SIGKILL` 掉持有 lease
的那一片，另一片在 **28 秒／34 秒**（兩次）接手並開始做合併與告警，
`takeovers` 記成 1。生產設定（快迴圈 60 秒 → TTL 180 秒）下最糟是三次
告警評估沒做。

**正常關閉。** 這一輪發現的問題：`SIGTERM`（`docker stop` 與 systemd 送的
第一個訊號）沒有 handler 的話，Python 直接就地結束 —— trap 埠不會關、
engine 池不會關、這個行程持有的 lease 留著自己過期。現在 `main()` 會接
`SIGTERM`/`SIGINT`，把兩個迴圈收掉、放掉 lease 再結束：

```
INFO - Stopping on signal
```

放掉 lease 的意義是**立刻**交接，而不是等一個 TTL；放掉自己的 heartbeat
的意義是重啟不會被報成「少了一片」。

### 24.9 資料庫連線數

這是分片唯一一個會意外撞到上限的地方。每個行程有自己的連線池
（`max(10, COLLECTOR_CONCURRENT + 5)` 加上 20 的 overflow），所以連線數
跟著行程數成長。實測（100 台、`COLLECTOR_CONCURRENT=20`，跑的時候取樣）：

| 行程數 | 尖峰連線數 |
|---|---|
| 1 | 20 |
| 2 | 28 |
| 4 | **81** |

PostgreSQL 預設 `max_connections=100`。所以四片已經在邊緣，再多要麼調大
`max_connections`，要麼把每片的 `COLLECTOR_CONCURRENT` 調小（分片之後
每片的設備本來就變少了，所以調小不見得會變慢）。這一條寫進
`docker-compose.yml` 的註解裡了。

## 26. 這一輪的侷限

* 量測主機只有 4 核，而四個模擬 agent 也在同一台上。四片的數字因此含
  7.6% 的競爭（24.5 節用單獨跑的同一片量出來的）。真實部署的設備在別處，
  所以那一部分會更好，不會更差。
* 分片的加速是在 400 台上量的，500 台與 1000 台是用「每台成本」外推。
  每台成本本身在 400 台直接量到（65.5 ms），而且與上一輪用不同方法量到的
  65.3 ms 相差 0.3%，所以外推的基礎比上一輪紮實。
* 兩片以上同時寫同一張表的競爭仍然沒有在高負載下實測。欄位不相交、
  批次寫入都依主鍵排序（第 20.1 節），而且分片之後**連列都不相交了** ——
  每條線只有一個行程會寫它的狀態與流量 —— 但這還是設計保證。
* lease 的接手時間是在 TTL 30 秒（快迴圈 4 秒）下量的。生產預設是 180 秒，
  沒有實際等過三分鐘。
* 自動發現的重複量是「一次」，但那是在「兩片各一台設備同時看到同一個新
  鄰居」這個特定場景下。真實機群有多少這種鄰居沒有量 —— 要看的話是每片
  log 裡的 `dead_ends`。
* 片數改變（例如 2 → 4）時每台設備的歸屬會變，退避狀態會重算。沒有為
  「換片數」做任何搬遷，因為代價就是每台設備多一輪探測。

# 第六輪：不要為一個掉包叫人起床

## 28. 告警抑制

這一輪不是效能，是**告警的可信度**。問題是這樣問出來的：既然每一個告警都
來自一次 UDP 交握，那掉一個封包會不會就發出一個假告警？

### 28.1 先盤點：誤報從哪裡來

`SNMP_RETRIES=2` 是每個請求打三次，所以**掉一個封包本來就不會變成告警**；
要三次都掉才算這台沒回應。但三個封包走同一條路，壅塞的上行或正在忙的 agent
可以一次吃掉三個。所以在這一輪之前，實際的行為是：

| 來源 | 一次錯誤的量測會怎樣 |
|---|---|
| 設備沒回應 | `status=offline` 立刻寫下去，同一輪的告警檢查就發 critical，下一輪回來再自動解除 —— 一組假的 `device_offline` + `device_online` |
| 線路 flapping | 每抖一次就一組 `link_down` + `link_up`。一條每分鐘抖一次的光纖 = 每分鐘兩筆，而最需要被讀的那條線的歷史最先變得讀不下去 |
| trap | 一個沒有回執、任何人都能偽造的 UDP 封包直接發告警 |
| 存檔失敗 | **`store_poll_result()` 的 except 分支也寫 `status=offline`** —— 設備好好地回答了，是資料庫寫入失敗，結果變成一個關於健康設備的 critical。這是個 bug，這一輪一起修掉（那個分支現在不碰 status） |

而輪詢讀到的 `link_down` **不需要**確認次數，這點值得寫清楚：埠的
`ifOperStatus` 跟「設備活著」是同一個 GET 回來的，所以封包既然收到了，
down 就是設備自己說的，不是掉包推論出來的。利用率也一樣不需要 ——
它本來就是一個間隔的平均，而且計數器倒退時產出的是「沒有速率」而不是
一個巨大的速率（第 6 節）。所以這一輪只動三個地方。

### 28.2 `ALERT_OFFLINE_CONFIRM_CYCLES`：連續幾次才算離線

連續 n 次沒回應才把設備判為離線。沒到 n 的時候**什麼都不寫** ——
設備保持原本的狀態，所以不發告警、也不會把既有的告警解除掉。計數器兩個
迴圈共用（快迴圈通常是確認的那一個），而且**只有連續**才算：答對一次就
歸零。

這裡有一個不明顯的互動：離線退避（第 11 節）會把失敗過的設備往後延，
而延後的那幾次就是要用來確認的那幾次。所以 `OfflineBackoff` 也拿到這個
數字，確認窗內維持正常間隔：

| 連續失敗次數 | 下次重試（快迴圈 60 秒） | 原本（confirm=1） |
|---|---|---|
| 1 | 60s | 60s |
| 2 | **60s** | 120s |
| 3 | **60s** | 240s |
| 4 | 120s | 480s |

沒有這一步，「連續三次」在 60 秒的快迴圈上要花 60+120+240 = 7 分鐘而不是
3 分鐘 —— 確認窗會變成退避曲線的函數，而不是你設定的那個數字。

**實測**（真的跑 `app.collector.main()`，殺掉一台模擬交換機，量「死掉」到
`device_offline` 那一列出現的牆上時間）：

| 設定 | 快迴圈 | 真的離線後多久告警 |
|---|---|---|
| confirm=1 | 5s | **4.2s** |
| confirm=3 | 5s | **24.3s** |
| confirm=5 | 5s | **44.4s** |
| confirm=3 | 20s | **99.1s** |
| confirm=3（退避不知道確認窗） | 20s | 119.1s |

大約是 `confirm × 間隔`，再加最多一個間隔的相位（設備可能剛好在一輪剛跑完
之後才死）。換到生產預設的 60 秒快迴圈：confirm=3 ≈ 3 分鐘出頭。

這就是這個旋鈕的全部內容：**用 (n−1) 個快迴圈的延遲，換掉「壅塞一次就叫人
起床」。** 要不要換、換多少，取決於網路本身有多穩，所以預設是 1（原本的
行為），不預設幫人決定。

### 28.3 `ALERT_LINK_FLAP_TRANSITIONS`：一個故障一個告警

一條線在 `ALERT_LINK_FLAP_WINDOW` 秒內變化這麼多次就算 flapping。之後
「又 up 了」不再解除它的告警，而是把告警按住並在訊息與 `details` 裡說明
原因，直到這條線安靜滿一個窗為止。

三個刻意的設計：

* **第一次 down 永遠不延遲。** 一條斷掉就不動的線，告警時間跟沒有這個
  功能時一模一樣。被壓掉的是後面那一串恢復與重發。
* **只有「變化」才算。** 連續十輪看到 down 是一個事件，不是十個。否則
  一條斷掉的線每輪都會讓自己更像在 flapping。
* **`NULL` 不算。** 設備不可達時每條線寫的是 NULL（不是 down），而 NULL
  根本不送進計數器 —— 否則一台設備失聯會看起來像它底下每一條線同時在抖。

**實測**（真的 trap 封包，從模擬交換機自己的位址送）：一條線 8 次狀態變化
產生 **2 列告警（其中 1 列還開著）**，而不是 4 組告警＋恢復。按住的那一列
寫的是
`Link flapping: damp-a Gi1/0/1 -> damp-b Gi1/0/1 - 3 state changes in the last 10 min, holding the alert open until it settles`。
而且在按住期間，狀態沒變的那些輪次**一列歷史都不寫** —— 否則一條正在抖的
線會每分鐘生一列 `updated`。

### 28.4 `ALERT_TRAP_REQUIRES_POLL`：trap 要不要等輪詢同意

trap 的意義就是毫秒級的延遲，所以預設仍然是「收到就發告警」。但有些設備的
trap 要跨一段你不控制的網路，而 v1/v2c 的 community 等於明文密碼。所以現在
可以按設備選：

* **false（預設）** —— 通知本身就發告警。實測 49 ms（第 21 節）。
* **true** —— **狀態照寫**（拓樸和介面立刻是最新的，實測 65 ms），但
  告警交給下一次快迴圈。代價是最多一個快迴圈；換來的是遺失、過期或偽造的
  trap 永遠叫不醒人。

per-device 的覆寫放在告警設定檔的 thresholds JSON 裡
（`{"trap": {"requires_poll": true}}`），因為那本來就是「這台設備的告警
政策」，而 API 原封不動地傳遞它。設定頁面也給了它一個勾選框 —— 順便修掉
一個會咬人的地方：`saveProfile()` 原本是把 thresholds **整個重建**再送出，
所以任何它不認識的鍵（也就是這個政策）會在有人改一下 CPU 門檻的時候被
靜靜地丟掉。現在它先把既有的內容攤開再覆寫自己那三個指標。核心交換機的 linkDown 可以維持毫秒，
分公司那一櫃可以要求佐證 —— 這是同一個機群裡兩種不同的判斷，所以不能只有
一個全域開關。

兩個實測的場景：

| 場景 | 結果 |
|---|---|
| 對一條**實際是 up** 的線送 linkDown | 狀態寫下去（65 ms）、不發告警；下一輪輪詢把狀態改回 up —— **從頭到尾沒有人被叫** |
| 對一條**實際是 down** 的線送 linkUp（偽造的恢復） | 狀態跟著 trap 寫成 up，但**告警沒有被解除**；下一輪輪詢把狀態寫回 down，同一列告警還在 |

一個限制寫在程式裡也寫在這裡：`COLLECTOR_FAST_INTERVAL=0` 時沒有任何東西
在輪詢每條線的狀態，「等輪詢佐證」就等於「永遠不告警」。那種設定下
collector 會警告一次並維持立刻告警，而不是安靜地把 trap 吞掉。

### 28.5 成本：沒有多一句查詢

這三件事都是**行程內的記憶體**，不是資料庫狀態。分片之後一台設備剛好一個
主人、整機群的告警檢查剛好一個行程在做（第 24.2 節），所以沒有東西需要
跨行程協調 —— 這也是它們可以不碰資料庫的原因。

在 cycle4 的 500 台機群上量（10,324 條線，其中 **491 條是 down 的** ——
遠比健康機群糟）：

| | CPU | 查詢數 |
|---|---|---|
| 告警檢查一輪，抑制關閉 | 13.4 ms | **3** |
| 告警檢查一輪，抑制開啟 | 13.2 ms | **3** |

同樣 3 句，差異在雜訊內。純記帳的部分：

| 動作 | 成本 |
|---|---|
| 10,000 條線每輪各記一次狀態 | 5.4 ms CPU（**0.54 µs/條**） |
| 10,000 條線的 `prune()` | 2.96 ms |
| 10,000 條線**同時都在 flapping**（最壞情況）的記憶體 | 2.7 MB（281 bytes/條） |
| 500 台設備全部失聯時的失敗計數 | 0.47 ms/輪 |

（那 281 bytes 是一次調整的結果：原本每條線用一個 `deque` 存時間戳，量到
953 bytes/條，換成 3 個元素的 list 之後 281 bytes，順便讓記一次狀態從
1.19 µs 降到 0.54 µs。）

### 28.6 不改預設就不改行為

三個旋鈕的預設值都重現加入它們之前的行為：確認 1 次、不做 flap 抑制、
trap 立刻告警。`cycle4.py` 跑出來逐位不變（`raw_links=10324`、
`merged_links=922`、穩態快迴圈 **13 句**），前五輪的全套回歸也全部通過 ——
包含 `e2e_traffic` 那一項「不可達的設備 status=offline、backoff failures=1」。

## 30. 這一輪的侷限

* 延遲表是在 5 秒與 20 秒的快迴圈上量的，生產預設的 60 秒是按
  `confirm × 間隔 + 相位` 外推。那個公式本身在三個間隔上都成立
  （4.2/24.3/44.4 與 99.1），但沒有真的等過 3 分鐘。
* flap 的狀態是**行程內**的。分片之後整機群的告警檢查在哪個行程跑是由
  lease 決定的，所以持有者換人時 flap 歷史會重算 —— 一條正在抖的線會
  重新累積它的次數（最多多一組告警＋恢復）。接手本身是分鐘級的事件，
  所以沒有為它做持久化。
* 確認計數同樣是行程內的。collector 重啟時正在確認中的設備重新數 ——
  偏向「不發告警」而不是「多發告警」，而已經在告警的設備不受影響
  （那一列在資料庫裡）。
* 兩個迴圈共用一個計數器還有一個副作用：**只有盤點迴圈失敗**的設備
  （快迴圈的 3 個 varbind 回得來，但整張表的走訪超時）在 confirm > 1 時
  可能永遠確認不了 —— 快迴圈每次成功都把計數歸零。這其實比較正確（那台
  設備確實是通的，問題在走訪本身），而且 log 裡每輪都有
  `FAILED (n/3 ...)`，但它確實不會再變成 `device_offline`。confirm=1
  （預設）沒有這個行為。
* 「10,000 條線同時 flapping」的 2.7 MB 是算出來的最壞情況，不是看過的
  機群。真實機群裡 `prune()` 每輪把安靜下來的線丟掉，字典只留下正在
  出事的那些。
* `ALERT_TRAP_REQUIRES_POLL=true` 的延遲上限是一個快迴圈，但那是指
  **告警**；狀態仍然是毫秒級。如果有人只看 `raw_links.oper_status`
  做自動化（而不是看告警），對他們來說這個旋鈕沒有任何差別。
* 沒有做「每台設備自己的確認次數」。目前是全域一個數字加上 trap 的
  per-profile 覆寫；要按設備調整確認次數的話，profile 已經是放它的地方。

## 32. 鎖定依賴、型別檢查與測試進 CI

第 31 節第 2 項。動機是這個專案唯一一次真的部署事故：部署出去的 v1.x 在
pysnmp 的 asyncio 進入點改掉之後，LLDP 走訪變成**回傳 0 筆、不丟任何錯誤**，
從外面看就是拓撲圖空白。`requirements.txt` 當時寫的是範圍，所以同一份原始碼
在兩天安裝出來的是兩棵不同的依賴樹，而失敗是安靜的。

### 32.1 鎖定之後抓到的四個問題

把直接依賴搬到 `requirements.in`、用 `pip-compile --generate-hashes` 產生
`requirements.txt`（40 個套件、每個帶 hash），然後**只用那份 lock 建一個乾淨
的 venv**。四件事當場浮出來：

| 問題 | 症狀 | 處理 |
|---|---|---|
| `sqlalchemy>=2.0.0` 沒有 `[asyncio]` extra | 乾淨環境 import 就死：`The SQLAlchemy asyncio module requires that the Python 'greenlet' library is installed` | 改成 `sqlalchemy[asyncio]` |
| `aiosqlite` 根本沒宣告 | `app/config.py` 的預設 `DATABASE_URL` 就是 `sqlite+aiosqlite://`，照文件走的人第一個查詢就失敗 | 加進 `requirements.in` |
| `alembic`、`apscheduler`、`redis` 三個都沒有任何程式 import | 白裝、白佔映像檔、白增加更新面 | 從 `.in` 移除，並在檔案裡寫明什麼時候該放回來 |
| `python-dotenv` 其實是 `pydantic-settings` 的傳遞依賴 | 不是錯，但它不該出現在「直接依賴」那一份 | 只留在 lock 裡 |

前兩個是**真的會讓新部署起不來**的 bug，而且在這之前無法被任何測試發現 ——
因為所有既有環境都已經間接裝到了 greenlet 和 aiosqlite。

`Dockerfile` 與 `deploy.sh` 都改成 `pip install --require-hashes`：hash 已經
在檔案裡了，明寫出來是為了讓「有人手改一行、少一個 hash」在建置時就失敗，而
不是安靜地裝到當天 PyPI 上的任何版本。

### 32.2 pyright 抓得到什麼，抓不到什麼

誠實的結論：**它抓不到當初那場事故**。

那次壞掉的是 `from pysnmp.hlapi.asyncio import bulkCmd` —— 一個不再存在的
名字。實測在同一份 pysnmp 上寫這一行，pyright **不會報錯**，因為
`pysnmp/hlapi/asyncio/__init__.py` 整個是 `from ... import *` 的再匯出，
型別檢查器對那個模組的符號表本來就是不完整的；而且程式現在自己用
try/except 包著兩個版本的進入點，所以就算檢查器看得懂也不該報。

它抓得到的是**整個模組不見**和**名字沒定義**。驗證方式是直接製造一次迴歸：
在 `app/core/traffic.py` 加上 `import redis`（剛剛從依賴移除的那個）與一個
不存在的函式呼叫，pyright 立刻紅：

```
app/core/traffic.py:138:8 - error: Import "redis" could not be resolved (reportMissingImports)
app/core/traffic.py:142:12 - error: "undefined_helper" is not defined (reportUndefinedVariable)
```

這正好是這一輪自己製造的風險：移掉三個沒人用的套件之後，如果真有誰在用，
CI 會在合併前說。

規則集刻意很窄（`pyrightconfig.json` 裡寫了原因）。pyright 預設的
`standard` 等級在這份程式上報 **177 個錯誤，而且沒有一個是 bug**：

| 規則 | 筆數 | 為什麼 |
|---|---|---|
| `reportArgumentType` | 84 | 同下 |
| `reportAttributeAccessIssue` | 46 | 資料模型還是舊式的 `Column()` 宣告，所以 `alert.is_active = True` 在檢查器眼裡是「對一個 Column 賦值」 |
| `reportGeneralTypeIssues` | 26 | 同上 |
| 其他 | 21 | 多數是 Optional 收窄跨不過方法邊界（例如 `_walk_cache_key()` 保證 `_walk_cache` 非 None，但那個保證在另一個方法裡） |

一個從第一天就是紅的關卡等於沒有關卡，所以先把能乾淨通過、又真的抓得到東西
的規則打開。要解鎖剩下的，得把模型從 `Column()` 搬到 `Mapped[]` /
`mapped_column()` —— 那是一次會碰到每個查詢的改動，列在第 34 節。

順手修掉一個真的被它抓到的東西：`get_db()` 標成 `-> AsyncSession`，但它
`yield`，所以型別應該是 `AsyncGenerator[AsyncSession, None]`。FastAPI 是靠
檢視函式本身決定怎麼處理依賴，所以行為沒變，但那個標註本來就是假的。

### 32.3 真正守住那場事故的是測試

既然型別檢查抓不到「走訪回傳 0 筆」，那就得有東西去真的問一次。
`tests/` 進了 repo（之前所有測試都只活在我的工作目錄裡）：

| 檔案 | 需要什麼 | 斷言什麼 |
|---|---|---|
| `test_snmp_collector.py`（7 項） | 一個 snmpsim 代理 | **筆數**：`ifDescr` 48 筆、`lldpRemSysName` 3 筆、鄰居解析出 sysName 與管理位址、down 的埠讀到 2 而不是 None、不存在的設備回 None 而不是空 dict、計數器真的在動且推得出 bps |
| `test_damping.py`（29 項） | 什麼都不用 | 確認次數、flap 窗、第一次只是基準不算變化、prune 留下還 down 的那條、trap 政策的解析 |
| `test_sharding.py`（15 項） | 什麼都不用 | 每個 device id 恰好屬於一片、不可能的切片要 raise 而不是夾值 |
| `test_config.py`（18 項） | 什麼都不用 | `APP_LOG_LEVEL` 真的有效、認不得的值退回 INFO、抑制的預設值就是文件寫的那些 |

合計 69 項，完整跑一次 10.6 秒。

兩個設計上的細節：

* **模擬器裝在另一個 venv。** snmpsim 會拉 pysnmp 7.x —— 正是這個專案鎖著
  不要的那個大版本。裝在同一個環境裡，它會蓋掉被測的 pysnmp，測試就不再是
  在測 lock 裡那一份。分開之後模擬器只是一個另一個行程，透過 UDP 對話。
  （順帶發現 snmpsim 1.2.2 自己漏宣告 `pysmi`，乾淨安裝會在綁埠之前就
  ModuleNotFoundError，所以 `requirements-sim.in` 幫它補上。）
* **沒有模擬器時 skip，但 CI 不准 skip。** 在沒裝模擬器的機器上跑純邏輯測試
  不該是紅燈，所以 fixture 預設 skip；CI 設 `REQUIRE_SNMPSIM=1`，同一個條件
  就變成 fail —— 否則 CI 會在「什麼都沒測」的情況下變綠。兩個方向都實測過。

### 32.4 CI 的三個工作

`.github/workflows/ci.yml`（這個 repo 之前完全沒有 CI）：

| 工作 | 做什麼 | 買到什麼 |
|---|---|---|
| `tests` | 照 lock 裝 app + 測試依賴，另一個 venv 裝模擬器，跑 pytest | 走訪真的還活著 |
| `lock` | 用釘住的 pip-tools 就地重編三份 lock，然後 `git diff --exit-code` | 有人改了 `.in` 沒重編、或手改了 `.txt`，合併前就會知道 |
| `typecheck` | 照 lock 裝依賴（不然每個第三方 import 都是 unknown，等於沒檢查），跑釘住版本的 pyright | 不存在的模組與名字 |

`lock` 這個工作能穩定是因為 `pip-compile` 在輸出檔已經存在時不會主動升級已
釘住的版本（沒有 `--upgrade`），所以只有 `.in` 真的要求了不一樣的東西才會
產生差異 —— 不會因為某個套件今天發了新版就無故變紅。這一點實測過：連續重編
三份 lock，`git diff` 是空的。

## 33. 這一輪的侷限

* lock 是在 **linux / CPython 3.11** 上解出來的，`uvicorn[standard]` 的
  `uvloop`、`httptools` 這些就是依這個平台選的。這跟 `Dockerfile`

* 移除 `alembic`、`apscheduler`、`redis` 是靠「整個 repo grep 不到任何

* 測試裡那個模擬器是 snmpsim，不是真的交換機。它驗的是「我們這一側的走訪、
  解析、速率推算是對的」，不是「某台 Cisco 的 agent 會這樣回答」。真設備
  那一側只有現場能驗。
* pyright 現在的規則集抓不到型別錯誤，只抓名字與模組。這是刻意的取捨
  （32.2），但不要把它當成「這份程式通過型別檢查」。
* `tests/` 只覆蓋了前面幾輪成果的一部分 —— 快慢迴圈、trap 接收器、lease
  接手、分片的端對端行為仍然只在我的工作目錄裡跑過，沒有進 repo。那些需要
  多個模擬器與一個資料庫，搬進 CI 是另一件事。

## 35. 把分片與抑制狀態放進 API／UI

第 34 節第 2 項。問題很具體：抑制一旦打開，**「沒有告警」就有兩種意思** ——
真的沒事，或者某台正在確認中而刻意還不發。這個差別之前只存在收集器的 log
裡。少了一片也是：唯一的症狀是那些設備慢慢開始報離線，看起來像網路出問題，
而不是像「有個行程沒啟動」。

### 35.1 為什麼不能讓 API 自己回答

API 跟收集器是兩個行程、不共用記憶體，而確認計數與 flap 歷史是**刻意**留在
收集器行程記憶體裡的（第 30 節：分片之後一台設備只有一個主人，不需要跨行程
協調）。所以 API 讀不到它們。

更糟的是設定值。docker-compose 裡 `ALERT_*` 只設在 collector 服務上，所以
API 行程讀 `settings.alert_offline_confirm_cycles` 會拿到**預設值 1**，然後
很有自信地顯示給一個實際上等三輪的機群看。那比不顯示還糟。

所以做法是：每個收集器把自己正在做的事寫在**它本來就要續約的 heartbeat 那
一列**上（`collector_leases.status`，新的 JSON 欄位），API 只負責讀回來、
把 id 換成名字。設定值也一樣從那裡來 —— 顯示的是「正在跑的那個行程的值」。

一個附帶的改變：**單一收集器現在也會寫 heartbeat**。之前只有分片時才寫，
所以沒有分片的部署在資料庫裡完全沒有「收集器還活著」的痕跡 —— UI 連它有沒有
在跑都說不出來。

### 35.2 成本

| | 每輪 |
|---|---|
| heartbeat，沒有回報任何東西 | 2.34 ms |
| heartbeat，健康機群（status 320 bytes） | **2.31 ms** |
| heartbeat，50 台確認中 + 50 條 flapping（3,148 bytes） | 3.29 ms |

對照：500 台的快迴圈一輪是 1.27 s。也就是 **0.2%**，而且**沒有多一次查詢**
—— 續約那一句本來就要發，status 只是多一個欄位。

`cycle4` 逐位重現：`raw_links=10324`、`merged_links=922`、
`sum=9220000`、穩態快迴圈 13 句、`cables down=491`、`link_down` 491 筆。

### 35.3 驗了什麼

* **真的跑一次 `main()`**（`e2e_status`，17 項）：三台設備其中一台指向沒有
  東西在聽的位址，`ALERT_OFFLINE_CONFIRM_CYCLES=3`。API 回報
  `pending_offline: 1`，而且是 `dark-sw` 這個名字加上「第 2 次」，不是一個
  數字。收集器停掉之後 `reporting` 變成 false，但那一列還在、標成 not live
  —— 「收集器停了」跟「沒有收集器」是不同的事。
* **兩種資料庫都跑**（`status_db`，各 12 項）：寫入走的是 raw SQL 加一個
  JSON bindparam 和 `COALESCE`，這正是那種「SQLite 的 text 欄位能過、
  PostgreSQL 的 json 欄位會爆」的寫法。兩邊都驗了插入、更新、unicode 與巢狀
  結構、以及**不回報的續約不會把別人寫的 status 洗掉**（SQLAlchemy 預設會
  把 Python `None` 送成 JSON 的 `"null"`，那會讓 `COALESCE` 認為「有值」而
  覆蓋掉 —— 要 `none_as_null=True`）。還驗了「回報函式自己爆掉不會害行程
  掉 lease」：診斷不該變成依賴。
* **既有資料庫就地升級**（`status_upgrade`，各 7 項）：用舊版的欄位建表、
  塞一列進去，`init_db()` 之後欄位出現、既有的 owner 與 takeovers 都還在、
  status 是空的，然後收集器接手開始回報。不需要 migration。
* **真的開瀏覽器看**（Chromium + Playwright，17 項）：三片回報、第 2 片缺席
  的機群，頁面要出現缺片警告、確認中的設備名與「2/3」、flapping 的那條線
  （本地埠 + 對端）與「7 次狀態變化」、每一片一列、fleet-wide 的持有者、
  trap 計數。英文與正體中文各跑一次 —— 警告是 API 產生的，所以它帶 `code`
  與參數，由前端翻譯，不然中文介面裡會夾著英文句子。另外檢查沒有任何
  失敗的請求與 JS 例外。

### 35.4 這一輪的侷限

* `age_seconds` 是用 API 行程的時鐘算的，而 `live` 是資料庫的時鐘判定的。
  兩台機器的時鐘差很多的話，畫面上的「12 秒前」會不準，但綠燈／紅燈不會。
* status 是**續約時**的快照，所以畫面上的數字最舊可以差一個快迴圈間隔
  （預設 60 秒）。頁面每 30 秒重讀一次，重讀的是同一張快照。
* 收集器重啟時確認計數歸零（第 30 節），所以畫面上的「確認中」也會跟著
  歸零 —— 那是真的狀態，不是顯示問題，但看畫面的人會覺得數字跳掉了。
* `pending_offline_devices` 與 `flapping_link_ids` 每個行程各取前 50 筆。
  大規模斷電時畫面上看到的是其中一部分，但 `pending_offline` 的**總數**是
  完整的。
* 這一頁是唯讀的。從這裡改不了抑制設定 —— 那仍然是環境變數（全域）加上
  alert profile（per-device 的 trap 政策）。

## 37. trap 比對設備所有已知位址

第 36 節第 2 項，也是第 21.5 節留下來的那個洞：trap 接收器用**來源位址**對
`devices.ip_address` 認設備，而大部分平台預設是從出口介面送 trap。結果是
開 trap 就等於在每一台設備上加一行 `snmp-server trap-source` —— 在既有環境
裡，一台一張工單。那是這份實作的選擇，不是 SNMP 的要求。

### 37.1 改成比對什麼

盤點迴圈現在順便走訪每台設備**自己的 IP 位址表**，把它持有的位址記進
`device_addresses`，接收器拿整組去比對：

| 來源 | 什麼時候用 | 信任程度 |
|---|---|---|
| `devices.ip_address` | 一直 | 你輪詢它用的位址 |
| `device_addresses`（`ipAdEntAddr`，空的話 `ipAddressIfIndex`） | 一直 | 設備自己回報的，而且是**輪詢**時問到的 |
| v1 trap 的 agent-addr（RFC 3584 的 `snmpTrapAddress.0`） | 只有前兩者都對不上時 | 在封包裡，任何人都能寫 |

第三項只用來**找**設備，不會因此跳過任何檢查：那個埠上還是要有線，
`ALERT_TRAP_REQUIRES_POLL` 開著時還是要等輪詢同意，而且來源位址已經認出
某台設備時它不會蓋過去（實測：偽造的 agent-addr 指向 trap-a，從 trap-b 的
位址送出，結果算在 **trap-b** 頭上）。

**位址只從輪詢學，不從 trap 學。** 從 trap 學會讓任何人用一個偽造的封包把
自己的位址掛到某台設備上，然後以那台設備的身分送 trap。

兩張表而不是一張：`ipAdEntAddr` 在 IP-MIB 裡已經標為 deprecated 而且**每個
agent 都有**，`ipAddressTable` 是它的替代品而且是某些新韌體**唯一**有的。
先走第一張，空的時候才走第二張 —— 正常設備一次走訪。第二張的位址在列的
索引裡而不是值裡（`1.4.10.0.0.1` 是 IPv4 10.0.0.1），所以是另一條解析路徑，
兩條都對真的 agent 驗過。

### 37.2 成本，以及為什麼寫成一張每輪載入的索引

第一版是每台設備一個 SELECT 去對照它現有的列。量出來：

| 500 台、每台 3 個位址 | 每輪 |
|---|---|
| 每台一個 SELECT | **395 ms**（0.79 ms/台） |
| 一輪一個 SELECT，差異才寫 | **7.8 ms**（0.02 ms/台） |

所以改成跟 `RawLinkIndex` 同一個形狀（`app/core/device_addresses.py`）：
一輪開頭讀一次整張表，之後在記憶體裡比對，只有真的變了才寫。**位址沒有在
變動的機群，這張表每輪一句 SELECT、零次寫入。**

SNMP 那一邊的代價是實打實的，而且無法避免 —— 多一次走訪就是多一次走訪：

| 對 snmpsim（12 埠、2 個位址） | |
|---|---|
| `get_own_addresses` | 15.8 ms（p95 28.2，牆鐘延遲） |
| 對照：`ifDescr` 走訪 | 17.3 ms |
| ~~每台設備輪詢的 CPU，沒有它~~ | ~~100.2 ms~~ |
| ~~每台設備輪詢的 CPU，有它~~ | ~~110.5 ms（+10%）~~ |
| ~~500 台一輪的盤點~~ | ~~+5.1 s CPU~~ |

> **這兩行的 +10% 是錯的。** 它是一次不成對的 A/B（40 次開、40 次關，各跑
> 一次），而這台主機單次輪詢的 CPU 散佈比那個差值大。重新量過之後走訪是
> 一次輪詢的 **5.2%**（5.01 ms），而不是 10% —— 怎麼量錯的、怎麼重量的，
> 寫在第 38.2 節。下面那段「10% 換不到東西」的結論不變，數字換成 5%。

**預設是開的**，而這是一個取捨而不是免費的：不收 trap 的部署付了這些
CPU 換不到東西。選擇開著的理由是，預設關掉會讓「開了 trap 卻沒反應」這個
安靜的失敗重新出現 —— 而那正是這一項要消滅的東西。
`COLLECTOR_DEVICE_ADDRESSES=false` 關掉它，`Traps:` 那一行的
`known_addresses` 會掉回「一台設備一個位址」，設定頁的收集器狀態也看得到。

刻意**不**跟 `COLLECTOR_TRAP_ENABLED` 綁在一起：一台主機只有一個行程綁得到
udp/162，所以分片時拿到接收器的那一片需要其他片輪詢的設備的位址，而那些
行程的 trap 是關的。

### 37.3 驗了什麼

* **真的 trap 封包**（當初是 `e2e_trap_source` 12 項；第 39 節把這五個論點
  搬進 `tests/test_trap_e2e.py`）：trap-a 輪詢位址是
  127.0.0.2，它自己的位址表還回報 127.0.0.3。從 **127.0.0.3** 送一個
  linkDown —— 設備端沒有任何 trap-source 設定 —— 線路狀態變了、告警出現、
  linkUp 又解除。再驗三個反面：127.0.0.9（誰都不持有）照樣被忽略；NAT 後面
  的 v1 trap 靠 agent-addr 認出來；偽造的 agent-addr 蓋不過來源位址。
* **兩張 IP 表**（`tests/test_snmp_collector.py`）：同一台模擬設備，一個
  community 只有 `ipAdEntAddr`、另一個只有 `ipAddressTable`，兩條路徑都要
  解出同樣三個位址。沒有任何一張表的設備回空陣列，不是錯誤也不是猜測。
* **對照邏輯**（`tests/test_device_addresses.py`，8 項）：位址搬家之後只有
  新設備認得它（這就是為什麼要對照而不是累加）、沒變動時零寫入、刪設備時
  跟著消失、空字串不入庫。
* **認設備的邏輯**（`tests/test_trap_receiver.py`，22 項）：來源位址優先、
  其他位址也算、v1 宣稱只是最後手段、垃圾 agent-addr 被丟掉、每個未知來源
  只警告一次、管理位址在衝突時勝出。
* **兩種資料庫**：整套 120 項在 SQLite 與 PostgreSQL 各跑一次。順手修掉一個
  測試自己的問題：每個測試用自己的 `asyncio.run()`，而連線池裡的連線綁在
  開它的那個 loop 上，asyncpg 會丟 "attached to a different loop" ——
  SQLite 完全不會發作，所以那是個「本機全綠、對著真的資料庫才爆」的坑。
* **既有資料庫**（`addr_upgrade`，各 6 項）：舊資料庫沒有這張表，`init_db()`
  直接建出來、索引在、既有設備不動，不需要 migration。
* **`cycle4` 逐位重現**：`raw_links=10324`、`merged_links=922`、
  `sum=9220000`、穩態快迴圈 13 句。盤點那一輪從 1503 句變成 **1504 句** ——
  多的那一句就是每輪一次的索引載入。

### 37.4 這一輪的侷限

* **IPv4 only。** 接收器綁的是 udp4，比對的也是 dotted-quad，所以
  `ipAddressTable` 裡的 IPv6 列是直接跳過的。IPv6 的 trap 要先讓接收器聽
  v6，那是另一件事。
* **一台設備要先被成功輪詢過一次**，它的其他位址才算數。新加入的設備在第
  一次盤點（預設 300 秒）之前，trap 仍然只比對管理位址。
* 設備從一個**連它自己位址表都沒有**的位址送 trap（中間有 NAT 又是 v2c）仍然
  認不出來。那種情況還是得設 trap-source，或者把 `devices.ip_address` 改成
  它實際送出的位址。
* 位址表是**輪詢當下**的快照。位址在兩次盤點之間搬家的那段時間，舊設備會
  短暫地仍然匹配那個位址 —— 最多一個 `COLLECTOR_INTERVAL`。
  （第 38 節把走訪改成有間隔之後，這個窗變成
  `COLLECTOR_ADDRESS_INTERVAL` 加一輪盤點，預設約一小時。）
* ~~走訪是每輪都做的。~~ 第 38 節改掉了：每台設備最多每
  `COLLECTOR_ADDRESS_INTERVAL` 走訪一次。

## 38. 位址走訪的頻率，與一次被雜訊騙到的量測

第 37 節讓 trap 可以比對設備的所有位址，代價是盤點迴圈多一次 SNMP 走訪。
這一節把那次走訪改成**每台設備每隔一段時間才做一次**，順便更正第 37.2 節
一個量錯的數字。

### 38.1 為什麼可以不每輪做

位址是慢變數。介面的 IP 在有人去改它的時候改，不會在兩次輪詢之間自己變。
每 300 秒問一次跟每小時問一次，拿到的是同一張表 —— 只是前者付了 12 倍的錢。

所以 `app/core/device_addresses.py` 多了 `AddressWalkSchedule`：記每台設備
上次問到位址是什麼時候，`COLLECTOR_ADDRESS_INTERVAL`（預設 3600 秒）內不再
問。三個刻意的決定：

* **間隔寫成秒，不是輪數。** 寫成輪數的話，把 `COLLECTOR_INTERVAL` 從 300
  調到 900 會順便把位址的新鮮度變成三倍舊，而調的人不會知道。
* **沒走訪過的設備一律要走訪。** 間隔延遲的是「變動」，不是「第一次」——
  新加入機群的設備在它第一次成功輪詢就比對自己的位址，不是一小時後。
* **只有真的問到才記時間。** 沒回應的設備不記 —— 剛回來的設備正好是位址
  可能變過的那一台，不該因為它剛才不在就再放生一小時。

走訪的開關本來就是 per-call 傳進去的（`poll_device(ip, collect_addresses=)`），
因為一個 collector 被同一組認證的所有設備共用，「這台這次要走訪」不能是物件
上的旗標。那個參數**只能收窄**：傳 `True` 不會打開 `COLLECTOR_DEVICE_ADDRESSES`
關掉的功能，呼叫端不該有辦法開啟運維關掉的東西。

### 38.2 先更正第 37.2 節的 +10%

第 37.2 節寫「每台設備輪詢的 CPU 100.2 → 110.5 ms（+10%）」。那是用
`walk_cpu.py` 量的：40 次開著、40 次關著，各跑一次。把同一支腳本連跑三次：

| 第 37.2 節那支腳本，連跑三次 | |
|---|---|
| 第一次 | +15.5 ms（+16%） |
| 第二次 | +3.7 ms（+4%） |
| 第三次 | **−5.0 ms（−5%）** |

第三次量出「走訪讓輪詢變快」，這顯然不可能。所以那個 +10% 是雜訊，不是量測
—— 這台主機單次輪詢的 CPU 是 p10 76.9／p90 113.3 ms（150 次），散佈比要量的
差值大好幾倍。第 24 節的表格旁邊我自己寫過「同一組設定重跑的變異約 ±10%」，
然後在 37.2 拿一次不成對的 A/B 去講一個 10% 的差。

走訪不依賴輪詢的其他部分，所以可以單獨量，而單獨量就穩了：

| 同一個行程、同樣方式（snmpsim，12 埠、2 個位址） | |
|---|---|
| 一次盤點輪詢（不含走訪） | 95.6 ms（6 批中位數，91.8…107.1） |
| `get_own_addresses` 一次 | **5.01 ms**（6 批中位數，4.91…5.78） |
| 走訪佔一次輪詢 | **5.2%** |

也量了成對差值（150 對，一次關一次開，背靠背）：中位數 +2.29 ms，但 p10/p90
是 −17.6／+27.9 —— 連成對都蓋不住這台主機的雜訊。所以表格裡用的是隔離量測的
5.01 ms，它六個批次之間只差 0.9 ms。

### 38.3 省下來的

走訪的次數直接除以「一個間隔裡有幾輪盤點」（`COLLECTOR_INTERVAL` 預設 300）：

| `COLLECTOR_ADDRESS_INTERVAL` | 幾輪走訪一次 | 平均每台每輪 | 佔一次輪詢 | 500 台平均每輪 |
|---|---|---|---|---|
| `0`（舊行為） | 每輪 | 5.01 ms | 5.2% | +2.51 s |
| `900` | 3 | 1.67 ms | 1.7% | +0.84 s |
| **`3600`（預設）** | 12 | **0.42 ms** | **0.44%** | **+0.21 s** |
| `21600` | 72 | 0.07 ms | 0.07% | +0.03 s |
| `86400` | 288 | 0.02 ms | 0.02% | +0.01 s |

**這是攤平，不是削平。** 12 輪裡有 1 輪照樣付整個 2.51 s，其他 11 輪付 0。
那一輪的峰值跟改之前的每一輪一樣高，所以沒有新的峰值 —— 只是變少。目前所有
設備會在同一輪到期（上線時一起走訪，之後一起到期），要把峰值也攤掉就得把
到期時間打散，列在第 42 節。

盤點那一輪的 log 會說走了幾台：`..., 1504 addresses, 500 walked)`，沒走訪的
輪就沒有那一段。那是「這一輪為什麼比較慢」唯一需要的解釋。

### 38.4 代價：位址最多能舊多久

| | 延遲 |
|---|---|
| 新設備的位址 | **沒有延遲** —— 第一次成功輪詢就走訪 |
| 設備**多**一個位址之後 | 最多 `COLLECTOR_ADDRESS_INTERVAL`（3600） |
| ＋ 走訪只在盤點時發生 | ＋最多一個 `COLLECTOR_INTERVAL`（300） |
| ＋ 接收器的位址表有自己的快取 | ＋最多 `DEVICE_MAP_TTL_SECONDS`（60；未知來源最快 5 秒就會讓它重讀） |
| 預設下最壞 | **約 66 分鐘** |

這段時間裡，從那個新位址送來的 trap 會被忽略（log 裡一行、`ignored` 計數器、
設定頁的警告都看得到）。**不會漏掉事件**：線路狀態照樣由輪詢迴圈發現，最慢
一個 `COLLECTOR_INTERVAL`。換句話說，付出的是「trap 的即時性」而不是「監控
的正確性」。

反過來，位址**搬到另一台設備**之後，舊設備最多也還會匹配那麼久。接收器仍然
要求那個埠上有線、`ALERT_TRAP_REQUIRES_POLL` 開著還要等輪詢同意，所以後果
通常是「新持有者的 trap 被算到舊設備的某個沒有線的埠 → 忽略」，而不是對錯的
設備發告警。要縮短就把間隔調小，`0` 回到每輪走訪。

`AddressWalkSchedule` 是**行程記憶**，刻意的：它只決定「多久問一次」，所以
重啟最多就是全部再問一次（500 台 2.5 s），沒有任何需要持久化的東西。而剛
重啟的行程正好應該重新確認一次位址。

### 38.5 驗了什麼

* **端對端**（當初是 `bench9/e2e_walk_schedule.py` 15 項；第 39 節把同樣的
  論點搬進 `tests/test_trap_e2e.py`，所以現在 CI 每次都跑）：真的輪詢、
  真的換掉設備回報的位址、真的 trap 封包。順序就是這一節的論點：
  1. 第 1 輪兩台都走訪，學到 trap-a 的 127.0.0.2 與 127.0.0.3
  2. 第 2、3 輪**走訪 0 次** —— 而資料庫裡的位址一個都沒少（「沒問」不是
     「問了沒有」，不然會把整個機群的位址對照掉）
  3. 給 trap-a 加一個 127.0.0.5、重啟模擬器，第 4 輪照樣不走訪，新位址還
     不認得 —— 從 127.0.0.5 送的 trap 被**忽略**，線路狀態沒被碰
  4. 時鐘前進一小時，第 5 輪走訪，新位址進資料庫，**同一個 trap 被接受**
     （中間要等接收器自己的快取過期，這就是 38.4 那一行）
  5. 把 127.0.0.5 從設備上拿掉，下一次走訪它也從資料庫消失
* **單元測試 9 項**（當時 131 項，SQLite 與 PostgreSQL 各跑一次）：沒走訪過的
  設備一律到期、走訪過的在間隔內被跳過、一台的走訪不影響另一台、`0` 與負數
  都等於每輪、沒回應的設備不被記成走訪過、設備刪掉就忘掉；per-call 旗標只能
  收窄不能打開（對真的 agent 四種組合）；預設值 3600 本身也有測試，因為
  5.5 節的那個「約 66 分鐘」是從它算出來的。
* 時間用的是 `time.monotonic()`，所以主機時鐘往前跳不會讓某台設備多等一個
  間隔；測試注入假時鐘，一小時不用真的等一小時。
* **沒有新的 SQL**，而且 `cycle4` 重跑過了：500 台的盤點還是
  **1504 句**、`raw_links=10324`、`merged_links=922`、`sum=9220000`、
  穩態快迴圈 13 句 —— 跟第 37 節同一組數字。走訪跳過的輪根本不呼叫
  `apply()`，所以寫入只會變少，不會變多。
* 第 37 節的那套端對端（12 項）、位址對照的升級檢查（兩種資料庫各 6 項）、
  設定頁的 Playwright 檢查（19 項，多了一項看「間隔」欄的第三個數字）
  全部重跑通過。

## 39. 端對端的證據進 CI

前面每一輪的結論都有端對端的證明 —— 真的輪詢、真的 trap 封包、真的資料庫
—— 但那些腳本都在 scratchpad 裡，也就是**活在一個會被回收的容器裡**。CI 跑
的是單元測試、SNMP 走訪、收集器狀態與位址對照；那些最強的證據，一個都不在。
這一節把它們搬進 `tests/`。

### 39.1 多了什麼

| 檔案 | 項數 | 跑的是什麼 |
|---|---|---|
| `tests/test_loops_e2e.py` | 6 | `poll_all_devices()` 與 `FastPoller.run_cycle()` 本人，對 snmpsim 與真資料庫 |
| `tests/test_trap_e2e.py` | 5 | 真的 UDP trap 封包進真的 `TrapReceiver` |
| `tests/test_lease_e2e.py` | 11 | 租約與分片心跳，對真資料庫 |

| 迴圈那一組斷言 | |
|---|---|
| 一輪盤點 | 設備上線、廠牌、三條線（含 ifIndex 與埠速）、三個自己的位址 |
| 第二輪 | **一列都沒多、位址的列 id 一模一樣** —— 37.2／38.3 的成本量測就是建立在「沒變動就不寫」上面的 |
| 沒人應答的設備 | 判定 offline，而且沒有寫出任何線路 |
| 一輪快迴圈 | 每條線的 up/down 寫進去、唯一一條斷線的發 `link_down`、沒斷的不發 |
| 兩台互相報鄰居 | **合併成一條**（不是兩半、也不是三條），總頻寬 3000 Mbps |
| 兩輪之後的流量 | 是速率不是計數器（700 Mbps 進／10 Mbps 出的量級） |

trap 那一組就是第 37 節那五個論點，現在是測試而不是腳本：從設備**自己持有
的另一個位址**送來的 linkDown 會被套用並發告警、linkUp 會解除；誰都不持有
的位址被忽略而且線路沒被碰；NAT 後面的 v1 靠自己宣稱的位址認出來；**偽造的
宣稱蓋不過來源位址**（從 trap-b 送、宣稱是 trap-a，結果算在 trap-b 頭上）；
以及第 38 節買來的那個延遲 —— 走訪間隔內新位址送的 trap 被忽略，時鐘前進
一小時之後同一個封包被接受。

租約那一組補的是只有 SQL 層才看得到的事：兩個行程只有一個拿到整機群的工作、
過期之後**只被接手一次**、`release()` 不用等 TTL、心跳帶著回報的狀態整包
JSON 進出、**回報 None 不會把上一次的狀態清掉**（那就是
`JSON(none_as_null=True)` 那個洞）、狀態的 callable 爆掉只損失狀態不損失
租約、四片裡少一片會被指名。

### 39.2 兩個手法，以及為什麼不是作弊

**一個模擬器當好幾台設備。** snmpsim 按 community 挑錄音檔，而拓樸引擎是用
sysName 認設備的 —— 所以「兩個 community 互相把對方寫成 LLDP 鄰居」在上層
看起來就是兩台接在一起的交換機。合併那段邏輯只有這樣才測得到：一台受管設備
配一個非受管鄰居，`merged_links` 永遠是空的（這是對的行為，但也等於沒測到）。
同一個代理另外綁了 127.0.0.4，這樣 trap 才能從一台**受管設備**送出去 ——
偽造宣稱那個測試需要的正是「來源位址本身也是個合法設備」。

**換 community 等於換位址。** 「設備多一個位址之後要等下一次走訪」這件事，
中途重啟模擬器會把測試變成另一件事（重啟也會清掉行程記憶）。改成把設備的
community 指到另一個錄音檔：對收集器來說，下一次走訪就是看到不一樣的一組
位址，而那正是改位址的樣子。時間用注入的假時鐘，所以「一小時後」不用真的等。

全部 127.0.0.0/8 在 Linux 上都是本機位址，所以 trap 的來源位址是**真的**
來源位址，不是參數 —— 整個功能的意義就在這裡。

### 39.3 CI 現在跑兩次

`tests` 這個工作變成 sqlite 與 postgresql 兩條（`postgres:16` 的 service
容器）。不是為了保險：**有兩個已經發生過的錯只在 PostgreSQL 發作**，而
SQLite 兩個都不抱怨 ——

* 連線池裡的連線綁在開它的 event loop 上。這套測試每個用自己的
  `asyncio.run()`，所以第二個碰到資料庫的測試會拿到 asyncpg 的
  "attached to a different loop"。
* Python 的 `None` 預設會被當成 JSON 的 `"null"` 存進去，而 `COALESCE`
  認為那是個值 —— 回報 None 的收集器因此會把上一次的狀態蓋掉。

而這一輪就現場又碰到一次同一類：新加的 `clean_db` fixture 在自己的 loop 裡
建表，連線還回池子之後測試本體在另一個 loop 裡拿到它 —— 20 個新測試在
SQLite 全綠、對 PostgreSQL 全紅。修法是 fixture 在自己的 loop 結束前就把
engine dispose 掉（`tests/conftest.py`）。**這正是加這條 CI 的理由，而且它
在加上去的第一天就抓到東西。**

### 39.4 成本

| | |
|---|---|
| 整套（153 項，含 SNMP 與端對端） | **36.6 s**（SQLite）／36～40 s（PostgreSQL） |
| CI 的 `tests` 工作 | 兩條並行，所以牆鐘沒有變兩倍 |
| 最慢的一項 | 「沒人應答的設備」3.6 s |

那一項原本是 **45.7 s**：真的預設（SNMP 超時 5 秒、重試一次、放棄之前還有
好幾個 GET）就是這個數字 —— 那是一句關於「不可達的設備讓一輪付多少」的真話
（第 24 節的 backoff 就是為它存在的），但不是那個測試要驗的東西，所以只有
那一個測試把超時調成 1 秒。

### 39.5 還沒進 CI 的

* **`cycle4`**（500 台、真 PostgreSQL、語句數逐位比對）還是手動跑。它是成本
  量測而不是行為測試，而且要一個 500 台的 fixture；列在第 42 節第 4 項。
* **設定頁的 Playwright 檢查**（19 項）也還是手動跑，因為 CI 要多一個瀏覽器
  與一個跑起來的 API。
* 這兩個都還在 scratchpad 裡，所以第 39 節開頭那句話對它們還是成立的。

## 41. 可以上線了：認證、一鍵部署，以及把假的東西拿掉

前四十節都在「它測得準不準、跑得快不快」。這一節是另一個問題：**一台乾淨的
機器上，一個人要花多少力氣才能把它跑起來，而跑起來之後它安不安全。**

答案原本是：Docker Compose 跑得起來，但整個 API **沒有任何認證** ——
`app/main.py` 唯一掛著的 middleware 是 CORS，而且是
`allow_origins=["*"]` 配 `allow_credentials=True`。任何連得到 8080 的人都讀
得到每一台設備的**明文 community**、改得動設備清單、關得掉告警。這不是「設計
沒做完」，是這個專案從頭到尾假設它跑在一個完全可信的內網上，而那件事沒有被
寫下來，也沒有任何東西在守它。

### 41.1 認證放在哪裡，以及為什麼

放在反向代理上，不在應用程式裡。理由不是偷懶：

* 這個系統要保護的東西是「誰連得到這個管理介面」，不是「哪個使用者可以看
  哪一台設備」。前者一層 HTTP basic auth 就夠，後者要一套使用者模型 ——
  而這個專案連使用者的概念都沒有，發明一套會碰到每一個 endpoint。
* 放在代理上，應用程式之後怎麼改都不會把這一層弄丟。

所以：

| | 之前 | 現在 |
|---|---|---|
| 應用程式 8080 | `0.0.0.0:8080`，對整個網路開 | `127.0.0.1:8080` |
| 資料庫 5432 | `0.0.0.0:5432`（裡面有全部的 community） | `127.0.0.1:5432` |
| Redis 6379 | `0.0.0.0:6379`，無密碼 | `127.0.0.1:6379` |
| 唯一入口 | 無 | nginx 443（80 一律轉過去） |
| 認證 | **無** | HTTP basic auth，密碼在部署時隨機產生 |
| `/docs` | 開著（可以直接打 API） | 要密碼 |
| 健康檢查 | 只有 `/health`（永遠回 healthy） | `/health` 免認證＋`/health/ready` 真的 `SELECT 1` |
| CORS | `*` ＋ credentials | 預設不掛，`APP_CORS_ORIGINS` 指名 |
| TLS | 無 | 自簽（部署時產生），basic auth 的密碼才不會走明文 |
| 資料庫密碼 | 寫死 `topomon` | 新安裝隨機；既有部署沿用舊值（密碼烤在 pgdata 裡） |

`127.0.0.1:5432` 這一條有個要注意的地方：collector 走 `network_mode: host`，
所以它仍然連得到 `localhost:5432`。綁回 loopback 只擋掉網路上的其他人。

### 41.2 一個設定檔變成八個測試

`deploy/nginx.conf` 是現在整個專案的認證，而它是一個**只有人會讀的檔案**，
也就是最容易漂掉的那一種東西 —— 一個 `auth_basic off` 就全開了，而從外面看
不出任何差別。所以它跟 SNMP 走訪一樣，用真的東西測：

`tests/test_proxy_auth.py` 會起一個**真的 nginx**，餵它**部署出去的那一份
設定**（只替換 upstream 位址與兩個埠），後面接一個會記錄「我被要求了什麼
路徑」的假應用程式，然後斷言：

| 項 | 斷言 |
|---|---|
| 沒帶密碼 | 401，**而且假應用程式沒有收到任何請求** —— 是代理擋掉的，不是應用程式 |
| 帶對密碼 | 200，請求有到 |
| 帶錯密碼 | 401，請求沒到 |
| `/docs` | 401（最容易忘的一個：那是可以直接打 API 的表單） |
| `/health`、`/health/ready` | 200，不用密碼（負載平衡器與 `topomon health` 要用） |
| `/health/../api/v1/devices` | 401 或 400 —— 免認證的是那兩條**路徑**，不是前綴 |
| 明文 HTTP | 301，而且**在問密碼之前**（basic auth 是 base64，不是加密） |
| 設定檔本身 | 只有一處 `auth_basic`，而且是那個 catch-all 的 location |

「假應用程式沒有收到請求」這一條是刻意的：一個 401 從客戶端看不出來是代理
擋的還是應用程式回的，而我們要證明的是**流量到不了應用程式**。

nginx 跟 snmpsim 同一個規矩：`NGINX_BIN` 找不到就 skip，CI 設
`REQUIRE_NGINX=1` 把 skip 變成失敗。CI 的 nginx 是 1.24（Ubuntu），比
`http2 on;` 需要的 1.25.1 舊，所以測試會在舊版上把那一行註解掉再跑；部署用
的映像釘在 `nginx:1.27-alpine`。

### 41.3 一行部署，以及更新失敗會自己退回去

```bash
export GITHUB_TOKEN=ghp_xxx
curl -fsSL -H "Authorization: Bearer $GITHUB_TOKEN" \
  https://raw.githubusercontent.com/nox913106/net-lldp-topo/main/install.sh \
  | sudo GITHUB_TOKEN="$GITHUB_TOKEN" bash
```

權杖要給兩次是因為**這個 repo 是私有的**：一次給 `curl` 拿這個腳本，一次給
腳本自己 clone。這一點是寫完文件之後去打那個 URL 才發現的 ——
`raw.githubusercontent.com` 對未認證的私有檔案回的是 **404 而不是 401**，
所以原本那個乾淨的一行不但不能用，失敗訊息還會讓人以為是路徑打錯
（41.5 的最後一段）。權杖由 git 寫進 `/opt/topomon/.git/config`，install.sh
把那個檔案收成 600；不想留權杖的做法（唯讀 deploy key）寫在
docs/DEPLOYMENT.md。

`install.sh` 只做「把機器準備好」：裝 docker、clone 到 `/opt/topomon`、然後
`exec tools/topomon deploy`。真正做事的是 `tools/topomon`，它也是之後維護用
的那一個指令（`health` / `update` / `status` / `logs` / `backup` /
`password` / `restore` / `rollback` / `uninstall`）。

三個決定值得寫下來：

1. **`/usr/local/bin/topomon` 是連結，不是複本。** 它指向 repo 裡的
   `tools/topomon`，所以 `topomon update` 做完 `git pull` 之後，下一次執行的
   就是新版的它 —— 不然「更新用的工具」要另外更新。
2. **`topomon update` 的健康檢查沒過就自動回滾**（`git reset --hard` 回更新
   前那個 commit，重建，再檢查一次），並且把失敗的日誌印出來。這個指令最可能
   是在沒有人盯著的時候跑的，而一個「更新完就壞掉而且不說」的部署指令比沒有
   這個指令更糟。
3. **密碼只在產生的那一刻印出來，不存回磁碟。** 所以 `topomon health` 檢查
   API 的時候不是帶著密碼從外面打，而是從 app 容器**裡面**打
   `127.0.0.1:8080` —— 繞過認證，是因為它本來就在認證的裡面。

`topomon health` 檢查的五條都是「會無聲壞掉」的東西：容器少一個（少了
collector，UI 會好好地顯示一份越來越舊的拓撲）、代理沒在聽、資料庫連不上、
**認證沒在要求**（直接打 `/` 看是不是 401）、沒有收集器在回報。全過才
exit 0，所以可以直接丟進 cron 或監控。

### 41.4 拿掉的東西

* **`POST /api/v1/discovery/start` 與 `GET /discovery/status`** ——
  收集器還不存在時的佔位實作。`/start` 會 `sleep(2)` 然後回報「發現 0 台、
  失敗 0 台」，而那跟「掃過了，網路上真的沒有別的設備」長得一模一樣。
  比 404 更糟的不是沒有答案，是一個看起來像答案的東西。發現真正發生在收集器
  （每輪從鄰居往外長）與排程器（掃網段），API 那一份是 `/manual`。
* **`docs/SDD-API.md` 的 WebSocket 一節**沒有刪，改成標明「未實作」並寫出
  缺的是什麼（收集器與 API 是兩個行程，推送要一條資料庫通知或 Redis
  pub/sub 的路，而 Redis 目前程式還沒在用）。前端是在輪詢的。
* **`deploy.sh`**（還在 clone 已經改名的舊 repo URL）、`cascade_result.txt`、
  `check_groups.py`、`verify_cascade.py`。

### 41.5 驗了什麼

| | |
|---|---|
| 全部測試 | **189 項通過**（原本 153，新增 36：代理 8、HTTP 介面 7、部署 21） |
| 代理那 8 項 | 對真的 nginx 1.24，跑部署用的那份設定 |
| `deploy/nginx.conf` | `nginx -t` 通過（`http2 on;` 在 1.24 上要註解掉，那是 1.25.1 才有的寫法） |
| `docker-compose.yml` | `docker compose config` 解析通過，五個服務 |
| 兩個腳本 | `bash -n` 通過；`topomon` 的 dispatch、usage 與 `cmd_*` 三份清單一致（測試在守） |

還有兩個是「驗了才知道」的。第一個：文件上那個乾淨的一行**不能用**。寫完之後去
`curl` 那個 URL，回的是 404 —— repo 是私有的，而私有檔案對未認證的請求回
404 不回 401，所以錯誤訊息會把人帶往「路徑打錯了嗎」。install.sh 現在吃
`GITHUB_TOKEN`／`TOPOMON_TOKEN`，所有 git URL 都由一個 `repo_url()` 組出來，
失敗時印的是「三個選擇」而不是 git 的原話，而且有三項測試守著（權杖只經過
那一個函式、沒有任何輸出會印到它、`.git/config` 兩條路徑都 chmod 600）。
教訓跟第 38 節同一個形狀：沒有去打那個 URL，這份文件就會是一句很有自信的
假話。

第二個更難看，而且是 CI 抓到的、不是我抓到的：修好上面那件事的同一個
commit 讓 `topomon --help` 在 CI 兩條腿都紅了，而我在這台機器上跑是綠的。
原因是 usage 的 heredoc 用的是**不加引號的分隔符**，所以我寫進說明裡的
`$GITHUB_TOKEN` 不是被印出來而是被**展開**，而 `set -u` 遇到沒設定的變數會
直接中止 —— 於是任何沒有 export `GITHUB_TOKEN` 的機器上，
`topomon --help`、`topomon`（不帶指令）與打錯指令全部回 1。

我這台有那個變數（這個開發環境的 GitHub 憑證），所以本地測試一路綠燈。這是
一個很典型的「測試跑在作者的環境裡」：

```
$ ./tools/topomon --help            ; echo $?     # 我這台
0
$ env -u GITHUB_TOKEN ./tools/topomon --help ; echo $?
./tools/topomon: line 640: GITHUB_TOKEN: unbound variable
1
```

修法是把那兩個 `$` 轉義。守它的有兩層，而且兩層都先確認「把 bug 放回去會
變紅」：

* 所有執行 CLI 的測試改成在**刻意貧瘠的環境**下跑（只有 `PATH` 與 `HOME`），
  所以作者 shell 裡的任何變數都不可能再遮住這類錯誤；
* 一個靜態檢查：兩個腳本裡對 `GITHUB_TOKEN`／`TOPOMON_TOKEN` 的每一次引用，
  要嘛加了 `:-` 預設值、要嘛被轉義、要嘛那個名字是腳本自己賦值過的
  （install.sh 的 `TOPOMON_TOKEN` 就是），註解行不算。

把那個轉義拿掉之後，五項測試會紅（三個 dispatcher、一個貧瘠環境、一個靜態
檢查）—— 在修之前它們只有靜態那一個會紅，另外四個是加了貧瘠環境才會。

**沒有驗到的：一次真的部署。** 這個開發容器裡沒有 docker daemon
（`/var/run/docker.sock` 不存在），所以 `install.sh` 的 apt 與 docker 安裝
路徑、`compose up` 之後的實際啟動順序、以及 `topomon update` 的回滾，都只有
邏輯被測過，沒有在一台真機器上跑過。第一次上線建議：先在一台測試機跑
`install.sh`，確認 `topomon health` 全綠，再跑一次 `topomon update`（應該
回報「已經是最新版」），然後才接真設備。
